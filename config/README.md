# config/ — Phase 0 CONFIG artefacts

First build artefacts of Phase 0 (`docs/architecture/ARCHITECTURE_PLAN.md` §17.2, *Deliverables — configuration and calibration*). **No engine exists yet** — these files are authored ahead of Phase 1 so the fail-closed baseline predates the code that will read it. Nothing here is wired to anything; the point is that when the first run ever executes, these files already exist in their honest state.

## The files

| File | What it is | Governing plan sections |
|---|---|---|
| `hard_excludes.yaml` | The hard-excludes baseline (fact class F-J) that must survive a knowledge-base outage: forbidden topics, framings, claim types, do-not-mention entities. Config carries the baseline, Notion may add, the **union always wins**; excludes are monotonic and never resolvable downward. | §6.3 (F-J), §6.4 asymmetry 1, §10.3, §11.3, OD-9 |
| `special_category_source_deny_list.yaml` | The GDPR Article 9 source/community deny-list, applied **before collection**: any source or community whose defining characteristic is a special category (health condition, political affiliation, sexual orientation, and the remaining Art. 9 categories). Disposition on match is always **do not store / delete**, never flag-and-continue. | §2.6 (consequence "special-category exclusion, applied twice"), §2.7 veto list, R4-M1 |
| `claim_ledger.yaml` | The claim ledger — what may be said — **seeded honestly empty**, with the full F-H record schema as a commented template. This location is a **default pending operator confirmation of OD-9** (recommendation: Notion-primary split with a config pointer; carried as a recommendation, not a lock). | §6.3 (F-H), §6.4, §6.5 cond. 4, §6.7, §16 OD-9, §17.2 |

## Fail-closed semantics (the rule all three files share)

- **Missing or unreadable file = stop.** Unresolved hard excludes and an unreadable claim ledger are degrade conditions 5 and 4 of §6.5 respectively — an unattended run degrades to research-only (completed-degraded, §11.3), and neither condition can be overridden even interactively. An unreadable deny-list means the §2.6 control cannot be enforced.
- **Empty list = valid.** "Missing is not the same as empty" (§6.3). An empty list is *resolved-empty*: a first-class, safe, deliberate statement that there are zero entries. An empty claim ledger means all outcome/proof claims are blocked and generation is steered to teaching framing (§6.7 class 4) — designed behaviour, not failure. **An honestly empty ledger is a valid Phase-0 outcome; an unreadable one is not** (§17.2).
- **Operator-supplied lists are marked as such.** Every list awaiting brand-specific values (banned topics, competitor names, denied communities…) is an explicit empty list with a comment; empty means no entries, **not** gate-off.

## What is deliberately *not* here

Research-side excludes (§10.2) and the rest of the §2.7 veto list are separate knobs, not part of these three artefacts. The claim gate (verification over generated bytes, §6.7) is engine code, not config. The playbook-layer config surface (`docs/plans/PLAYBOOK_LAYER/06_config_surface.md`) governs a deferred layer (Amendment B); only its authoring conventions are borrowed here — the engine plan governs content.

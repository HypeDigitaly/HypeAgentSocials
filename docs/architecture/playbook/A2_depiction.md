# A2 — Depicted-attribute claim checking

**Status:** design-phase amendment, Amendment A (safety, pre-Stage-5), task A2. Binding architecture, not a proposal. No code is written by this document; its output is content the merge task (A4) inserts into `ARCHITECTURE_PLAN.md` per the wire-in table at §10.

**Closes:** P-11 — *"Generated imagery makes unchecked claims"* (`00_MASTERPLAN.md` §1). The claim gate covers text, including text on pixels, but never what the pixels *depict*. An image of a dish not served, or packaging that does not exist, passes every gate today. The AI-generation disclosure is not a defence to a misleading-action claim about the product's own nature — a fact this document treats as load-bearing, not incidental.

**Severability.** This document assumes A1 exists and cites A1's gate-order statement (`A1_prohibited_outcome_gate.md` §3) as the single owner of the per-asset chain's ordering; it does not restate or redraw that chain, and any statement below about where a check "runs" is a statement about *what class 12 contributes at that point*, never a new drawing of the chain itself. Beyond that dependency, this document stands alone with zero playbooks defined: nothing below requires the pack registry, relation types, archetypes, angles, genres, CTA vocabulary, trigger lanes, node overlays, ranking profiles, the config surface, or any of `02_legal_claim_packs.md`'s fact classes other than F-W. Where annex `02`'s design assumes a playbook selects the depiction policy, §6 below states the engine-floor-and-theme-opt-in mechanism that is true today, with the playbook-level mechanism recorded as a deferred, non-breaking extension for Amendment B.

## 1. When generated imagery constitutes a claim about a real product

An asset **depicts a real sellable item** when both halves of a two-part test hold. **(a)** Its topic/offer pairing — already resolved by spin, before any image is generated — references an F-B catalogue entry (§6.3; today's only engine-owned offer record, since F-P and F-T, the richer per-item catalogues annex `02` §4.1 proposes for hospitality and e-commerce verticals, are Amendment B fact classes this document does not touch and does not need) that is a physical, digital or on-screen item with a definite, checkable appearance — a piece of merchandise, a packaged product, or, for a software offer, **its actual rendered user interface** — rather than a pure capability claim with no visual form at all ("sends for you" has nothing to depict; a product's dashboard does). **(b)** The generated image's subject is presented as, or reads to a viewer as, a depiction of *that specific item* — a product shot, an actual-screen capture, a "here's what's inside" image — rather than a category-level mood or lifestyle visual carrying no specific-item claim. A generic workspace mood shot illustrating an article about productivity is not a depicted-attribute claim; a photorealistic render captioned as the product's actual screen is.

**One clarification this document makes explicitly, because the source annex's own wording could be read to exclude it and the excluded reading is wrong.** Annex `02` §3.1 states part (a) as "rather than an abstract service or software feature," which is correctly aimed at excluding pure capability claims from this test — a claim like "handles outbound for you" has no pixels to check. It is not aimed at excluding a software product's own on-screen appearance, which is exactly as photographable as a plated dish: it has one actual current look, and a generated image can misrepresent it in the same concrete ways (a feature shown that does not exist, a UI state that is not current, fabricated on-screen numbers). This reading is required by the masterplan's own example — theme #1's "product-dashboard renders" — which names precisely this case as the one Policy A's engine floor removes (§7). A capability claim with no visual form stays outside this check and inside the ordinary claim-gate substrate's capability class (class 6); a screenshot-shaped depiction of an actual product surface sits inside this one.

**How the flag is set, stated because it determines whether any model call is involved (it is not).** The two-part test is evaluated once, at plan time — shot-list or slide-list composition (§4.2 stage 4) — from information spin has already resolved (the offer/topic mapping) plus the theme's declared depiction policy (§6). A shot row that names a specific F-B-catalogued item's actual appearance as its subject is flagged there, as a property of the *plan*, not discovered afterward by inspecting pixels. A shot row describing a category-level or mood visual is never flagged. This is what keeps check class 12 (§4) a pure provenance check: the classification question — does this asset's brief call for depicting a specific real item — is answered deterministically from the plan before any image exists, and the only question left for class 12 to ask afterward is whether the plan's flag is backed by a linked reference.

**Legal grounding, carried at the confidence gradings annex `02` §3.1 already established, not upgraded.** UCPD Art. 6(1)(b) treats the main characteristics of a product — composition, fitness for purpose, quantity, geographical or commercial origin, or the results to be expected from its use — as a misleading-action ground; an image is exactly a claim vehicle for composition, quantity and appearance. Reg. (EU) 1169/2011 Art. 7(1) is more directly on point for food specifically and is textual, not inferred: food information must not be misleading as to a food's nature, identity, properties, composition or quantity, **"in particular... by means of pictures or other similar means."** Both are graded Medium-High confidence — well-established provisions, not independently re-verified against primary EUR-Lex text this cycle — and both carry the same open-counsel dependency annex `02` already logs (OD-L5, OD-L4). Neither is promoted to a settled citation here.

**Why the burned-in AI disclosure does not cure this, stated precisely because it is easy to conflate the two.** The Art. 50 AI Act disclosure (§14.6) answers a *process* question — is this synthetic. UCPD and FIC misleading-imagery liability answer a *substance* question — does this depiction correspond to reality. Disclosing that an image is AI-generated no more excuses a materially false depiction of the actual item than disclosing "this photo has been retouched" would excuse one under ordinary advertising practice. §14.6 already states the governing rule for exactly this shape of question — the AI-disclosure obligation is **cumulative with, not a substitute for**, every other compliance obligation the asset carries — and this document does nothing more than name the second obligation the rule was always going to have to cover once generated imagery of real items existed at all.

## 2. Fact class F-W — reference imagery for real sellable items

| Class | Contents | Tier | Home structure | Consumer gate | May be legitimately empty? |
|---|---|---|---|---|---|
| **F-W** Reference imagery for real sellable items | Linked reference photo(s) per F-B-catalogued item, supply date, and a tenant attestation of current accuracy | **B**, as a per-asset precondition, not a run-level band input (see the §6.5 note below) | Typed database, linked from **F-B** item records (today's only engine-owned offer record; extends automatically to F-P/F-T when Amendment B adds them, without F-W itself changing) | Check class 12 (§4); the keyframe-acceptance rubric's sixth item (§5) | **Yes at item level, for any item never depicted.** No, once an item is flagged as depicted under Policy B — an undepicted item legitimately has no reference asset, and that is the normal state for most of a catalogue |

**Its identity is recorded as a new field on the existing per-asset provenance record (§14.6/§8.13), not a new subsystem.** The provenance record already carries delivered route identity and version, generation timestamp, a commercial-use-terms snapshot and the router transaction id (§12.2). F-W adds one more field to that same record: a pointer to the linked reference asset(s) this specific generated image was grounded against. Nothing about the provenance record's ownership, its completeness-is-a-publish-gate-check rule, or its degrade-to-plan-only disposition on incompleteness (§5.6, §12.2) changes — F-W is data the existing record now also carries, not a second ledger to keep synchronised with the first.

**The tenant attestation and the staleness discipline.** The record carries a tenant attestation that the reference is a current, accurate depiction of the item — not a stock photo, not a supplier's marketing shot of a different portion or configuration, not a discontinued item's old photo. This uses the same staleness machinery every other fact class already has (§6.5/§6.6) rather than inventing a second one: an unrefreshed reference beyond its freshness window degrades **that item's** depiction eligibility — the item simply becomes ineligible for Policy-B depiction until refreshed — and does not degrade the confidence band or any other item in the pack. This is deliberate and mirrors the existing per-entry quarantine principle already applied to F-H (a bad ledger entry quarantines that entry, not the pack): a stale reference for one product photo is not evidence that anything else in the run is wrong.

**No independent verifier exists for F-W, and that absence is why the human attestation in §8 is load-bearing rather than a formality.** Unlike F-B (site-verified) or F-G (site-verified), there is no independent channel this architecture can fetch to confirm a supplied photo genuinely depicts the current item — a live-site fetch confirms an offer exists and is described a certain way in text, not that a specific photograph is accurate. The tenant's own supply-and-attest action is the only source, which is exactly why check class 12 stays a provenance-presence check (§4) and the substantive visual judgement is placed on a human reviewer who can actually compare the two images (§8), rather than on an automated step that would have nothing independent to check against.

## 3. Check class 12 — deterministic-only, per the binding C-12 ruling

**This is stated unambiguously because it is the deliverable most likely to be got wrong.** `00_MASTERPLAN.md` §4a's ruling on C-12 is binding and is restated here in full, not re-decided:

> Check class 12 verifies that every asset flagged as depicting a real sellable item carries a linked, in-window reference in its provenance record. This is a pure provenance check with no machine-vision model call. "In-window" means the reference appears in the same asset context — a URL to the product page, a name, a SKU, an image hash — such that a human can confirm the depicted item matches the reference. A model-mediated comparison node that takes two images and judges their resemblance is **not** this check. It is deferred value with its cost named rather than promised and unbudgeted.
>
> The substantive visual comparison — is this item depicted as it is actually sold, with no alterations that mislead — is the human attestation's job. That attestation is required by `02` §2.5 [renumbered §8 in this document] and the review pack must show the side-by-side. The engine contributes only the gate: a provenance record and a coherent reference exist, preventing orphaned images with no grounding claim. The visual integrity of the depiction policy belongs to the operator's attestation and theme-level governance, not to a class-12 model call.

**What class 12 mechanically does.** For every asset flagged at plan time as depicting a real sellable item (§1), class 12 checks that the provenance record carries an F-W reference link that is *in-window* — a URL to the item's page, a name, a SKU, or an image hash present in the same asset context, sufficient for a human to confirm the match without the engine ever judging pixel resemblance itself. Under **Policy B**, a flagged asset with a valid in-window link is **VERIFIED**; a flagged asset with no link, an expired link, or a reference past its staleness window is **UNSUPPORTED** and blocks, using the eleven/twelve-class verdict vocabulary exactly as class 1 through class 11 already do (§6.7). Under **Policy A**, a flagged asset is **UNSUPPORTED and blocks outright regardless of whether a reference happens to exist** — Policy A means no depiction, full stop, and a reference existing does not change that; class 12's grounding test is only meaningful once Policy B is the theme's declared value. An asset never flagged at plan time — a mood shot, a category visual, anything Policy C's decorative framing already covers — receives **SAFE-NON-CLAIM** the same way a structural or self-referential statement does elsewhere in the substrate, before any grounding question is even asked.

**Class 12 is substantiation-shaped and belongs inside the ordinary claim-gate substrate**, which is the deliberate, stated contrast with the Prohibited-Outcome Gate A1 specifies. The Gate asks a question no evidence can answer and uses two states with no VERIFIED outcome, because nothing in this system can make its pattern lawful. Class 12 asks exactly the opposite kind of question — is this specific depiction evidenced — and evidence is precisely what cures it: a linked, in-window, unexpired F-W reference is a complete answer. This is why class 12 takes a check-class number and reuses the five-verdict vocabulary, while the Gate deliberately does not and could not.

**No new model node, and no new §5.4a per-call ceiling — say so explicitly, because A1's own semantic pass does add both.** A1's Prohibited-Outcome Gate needs a model call for its semantic paraphrase pass, and is honest about that: a fourteenth bounded node in §1.5's inventory, with its own per-call ceiling. Check class 12 needs neither. It is a lookup — does this asset's provenance record carry an in-window pointer — against data already resolved at plan time and already sitting on the provenance record. The text-node inventory `00_MASTERPLAN.md` §4 ruling C-1 fixes at thirteen (for text nodes) is unaffected by this document in either direction: A1 adds one bounded node outside that count for its own reason, and this document adds none, for the opposite reason — one control's cost is a real, named model call, the other's is a field comparison, and neither should be described as costing what the other one costs.

## 4. The two enforcement points

Mirroring existing enforcement patterns rather than inventing a third, per the source annex's own stated design intent (`02` §3.6) — but corrected against the canonical chain A1 already fixed as the single owner of ordering, because the annex's second point, read literally, names a moment in the chain where no image yet exists to check.

**(a) At keyframe acceptance (§4.2a), as a sixth rubric item, binary and non-negotiable like items 2 and 4.** The existing rubric checks five things before a ~$0.04 keyframe unlocks ~$0.30 of clip spend: brand and composition lock, no legible text, safe-box compatibility, person-policy compliance, motion plausibility. Items 2 and 4 are binary and non-negotiable in every mode because they are compliance surfaces, not quality ones; items 1, 3 and 5 are scored. Reference-grounding compliance belongs beside items 2 and 4, for the identical reason: **item 6 — reference-grounding compliance** — under Policy B, the keyframe's composition matches a linked, in-window F-W reference for the item its shot row flagged; under Policy A, the keyframe does not depict a real sellable item at all, regardless of what a reference might say. This is exactly the cheap, pre-clip-spend control point §4.1 already names as the single most important economic decision in the system, and it is where the fix belongs: authorising ~$0.30 of clip spend on a keyframe already known to depict an ungrounded real item is the same class of waste the whole keyframe-first design exists to prevent, one step earlier than discovering it at assembly. On failure, the existing disposition applies unchanged: regenerate within the already-budgeted keyframe variant count, and on exhaustion, degrade that slot to plan-only with the reason attached — clip spend is never unlocked by a slot with no accepted, compliant keyframe.

**(b) At the post-assembly overlay claim pass (§4.4), not at claim gate pass 2 — a correction to the source annex, stated because getting this wrong would silently reintroduce the defect.** Annex `02` §3.6 names claim gate pass 2 as class 12's second enforcement point. Per A1's gate-order statement, the canonical chain closes text-side claim gate pass 2 **before** media planning, media generation or assembly ever run — at the moment pass 2 closes, no keyframe, clip or master exists yet for a media-bearing asset, and pass 2's own promise (§14.3, §14 intro) is explicitly scoped to "the exact packed **text** bytes." There is nothing for a depiction check to compare against at that point. The correct second enforcement point is the **post-assembly overlay claim pass** — which §14's own text already names as the thing that makes "final on the exact bytes that ship" true for media the way pass 2 makes it true for text — because it is the first and only point after keyframe acceptance where the actual final rendered media exists, and where the general principle A1's gate-order statement inherits from §6.7/§6.10 ("any gate that runs before a rewriting step must be re-run after it") applies: a keyframe accepted at (a) can still be swapped for a different, ungrounded one during a repair or regenerate cycle (the immediate loop, §12.4; regenerate-media-only, §8.11), and the overlay pass is where that swap is caught, on the final bytes, before packaging. Class 12 at this point re-verifies the finished asset's flagged depiction against its provenance record's F-W link exactly as it did at keyframe acceptance, costing nothing additional beyond what the overlay pass already does for the deterministic text classes (§14 intro already lists classes 1, 2, 3, 5, 9, 10, 11 as running there; class 12 is added to that set).

No third enforcement point is introduced. Both are re-uses of enforcement moments this architecture already has for exactly the reason each already exists — the cheapest possible point before spend, and the last possible point before packaging.

## 5. The three-value depiction policy, and what may select it before Amendment B

| Value | Meaning | Selectable today by |
|---|---|---|
| **Policy A — no depiction** | Real sellable items may never be depicted in generated imagery; product or offer discussion stays textual, imagery stays category-level or brand-mood only | **Every theme, by default. This is the engine floor and requires no action to have.** |
| **Policy B — reference-grounded** | Generated imagery may depict a real sellable item, built from a linked, current F-W reference per §2, with the human attestation and side-by-side review of §8 | A theme, by explicit, named opt-in (below) — **not** a playbook, because no playbook layer exists yet |
| **Policy C — decorative/illustrative only** | Generated imagery may depict a product category or scene type, not claimed to be the specific tenant item, structurally framed via caption/CTA template (§4.4's slot discipline) as illustrative rather than documentary | A theme, by the same opt-in as Policy B; available for mood content even within a theme that has also opted into B, exactly as annex `02` describes it operating within a pack |

**The severability ruling.** Annex `02` §3.3 selects Policy B "at playbook level only by food & beverage and product/e-commerce" — a mechanism that requires the pack registry and playbook selection this document may not depend on. Two options exist: give the Gate no selection path at all until Amendment B (B and C dormant, every theme locked to A), or give a theme a direct, named opt-in today. **This document takes the second option: a theme may declare Policy B or Policy C for itself today, subject to named preconditions, without any playbook mechanism existing.** The precedent for this shape of control already exists in this architecture and is not invented here: hero-tier multi-shot promotion (§4.3) is engine-safe-by-default with an explicit, bounded, human-gated escalation path, never available by silent configuration drift. A theme's Policy-B opt-in is the same shape — a deliberate, visible, named escalation from a safe floor, not a quietly available setting.

**The named preconditions for a theme's opt-in to Policy B**, all of which must hold before the theme-readiness validation this architecture already runs for every other declared knob (§10.6) will accept the declaration:

1. **At least one F-B item has a populated, tenant-attested F-W reference** — an opt-in with zero references declared is a contradiction the readiness check refuses, the same shape as F-D's "no at least one segment" rule (§6.3).
2. **The human-attestation mechanism of §8 is available for that theme's review package** — trivially true, since it is engine floor and requires no configuration, but stated because a precondition that can never fail is not a precondition worth naming unless the reader can see why it cannot fail.
3. **The opt-in is an explicit, dated declaration**, recorded the same way other consequential theme-level state changes are already recorded in this architecture, not an implicit consequence of populating F-W — a theme may supply reference photography and never opt in, and F-W being non-empty must never itself be read as consent to depict.

**Why this is a widening from the floor, not a tightening, and why that is fine.** Every other per-theme knob this architecture treats as monotonic (hard excludes, the AI-content class) is tightening-only because the floor is already the safe end and any theme-level move must stay on the safe side of it. Depiction policy is different in kind: A is the safe floor and B is a genuinely more permissive value a theme may deliberately choose, under named preconditions, in exchange for a real capability. That is not a violation of the tightening-only principle stated elsewhere in this amendment (A1 §5) — that principle governs controls with no legitimate reason to ever loosen (a hard exclude, a claim-shaped pattern). Depiction policy has a legitimate, operator-confirmed reason to loosen — real product promotion is on the critical path (§9) — provided the loosening is itself gated by grounding, attestation and review, which is exactly what B requires and what a plain "off" toggle would not. **The relationship that must hold, and does:** a theme may tighten from whatever it has declared back down to A at any time, unilaterally; a theme may never declare "B without the grounding requirement," because that would not be Policy B at all, it would be the exact ungrounded generative mode this entire control exists to close off. When Amendment B's playbook layer ships and a playbook begins selecting B for a vertical, a theme's pre-existing opt-in is read forward as exactly the state it already was — a theme under a B-selecting playbook may still only tighten to A, never loosen past B — so nothing about today's opt-in needs to be revisited or migrated; it already is the state Amendment B's own tightening-only rule describes.

## 6. The capability removal, called out as intended

**Policy A as the engine floor removes an existing capability from theme #1.** Nothing in `ARCHITECTURE_PLAN.md` as it stands today prevents a generated image from depicting theme #1's own product — specifically, **a rendered image of HypeLead's actual dashboard or interface**, the case the masterplan itself names. §4.4's rule that "generative models are never asked to render message-bearing copy" governs on-image *text*, not the underlying scene; nothing today stops a keyframe whose brief is "show the product's dashboard" from being generated, accepted and shipped as a plain generative image with no reference grounding at all. That is precisely the P-11 gap this document closes, and closing it changes what theme #1 can produce today without further action.

**Under the behaviour-preservation invariant, this is a defect of the amendment unless named as an intended fix — so it is named.** The capability removed: an ungrounded generated depiction of the product's own screen or interface, produced without any linked reference and without the human side-by-side attestation of §8. The defect it closes: **P-11**, stated in exactly the terms `00_MASTERPLAN.md` §1 gives it — generated imagery making an unchecked claim about a real product's actual appearance, for which the AI-disclosure label is not a defence (§1 above).

**What theme #1 must do instead, under the engine floor.** By default, once this document merges, theme #1 sits at Policy A: any asset discussing the product visually uses category-level or brand-mood imagery — an abstract representation of the *idea* of a dashboard, a stylised scene, a still that makes no claim to be the actual screen — never a depiction presented or read as the real interface. This is a real, visible change to what theme #1's imagery looks like for product-focused assets, and it is the correct one: today's behaviour was never actually safe, it was merely unexamined, and preserving it unexamined is not what the behaviour-preservation invariant protects.

**What a theme-level opt-in to Policy B would require of theme #1, concretely, if the operator wants the capability back.** Per §5's named preconditions: current, tenant-attested screenshots of the actual product interface, supplied as F-W reference imagery and linked to the relevant F-B offer entry; the theme's explicit, dated opt-in declaration; and, per asset, the human side-by-side attestation of §8 before that specific asset can reach a publish decision. This is not a re-ban dressed as a process — it is the same trade every other tenant who wants real-item depiction makes, applied to theme #1's own product, and it is available the moment the operator wants it, not gated on Amendment B.

## 7. Designed so product promotion works, not so it is banned

The operator has confirmed real product promotion is on the critical path, and this control is sized against that, not against a hypothetical maximum-caution posture. At Policy B, with adequate reference photography already on hand, the marginal reviewer cost is a glance at two images already sitting in the review package side by side (§8) — the same order of effort as the burned-in-disclosure legibility checks §3.5's table already folds into existing review-depth bands at no separate line item. Concretely: a **carousel or document carousel**'s existing "slide-by-slide skim" already checks on-image text legibility and disclosure presence per slide at 3–5 minutes; the side-by-side comparison for any depicted item adds one more glance per flagged slide inside that same skim, not a second pass. A **feed still or hero visual**'s existing "look-and-read" pass, already ~1 minute, absorbs the same glance the same way. A **keyframe** review, already a look-and-read at the order of a minute per §4.2a's rubric, gains item 6 as one more binary check alongside items 2 and 4 it already performs in the same look. The **confirmation pass** — full playthrough, not yet measured — is unaffected in kind, because the side-by-side comparison happens once, in the review package, not once per frame of motion. Nowhere does this document add a review-depth row that did not already exist, and nowhere does it change an existing time estimate; it adds one glance-weight item to passes that already exist for other reasons, which is the design intent stated in §9: the expensive failure mode this closes is specific and real (a tenant depicting an item it does not actually have, in the form it does not actually take), and the fix is grounding and a cheap human glance, not prohibition.

## 8. Human attestation and what the review pack must show

**A new, separately-recorded acknowledgement**, distinct from the AI-label acknowledgement (§14.6, §7.7) and from the editorial-responsibility field (§11.4), for the same reason those two are already kept separate rather than folded into general pack approval: **bundling is how a busy operator skips it.** Its wording:

> *"I have compared this generated image against its linked reference asset(s) and confirm the depiction is not materially misleading as to composition or contents, portion size or quantity, packaging, colour, or any accompaniment not included in the actual offer."*

For that acknowledgement to be a judgement rather than a rubber stamp, the review pack must **show**, not merely link to, four things, all inside the package itself rather than one click away:

1. **The reference asset and the generated image, side by side, in the review package itself** — the identical "both values side by side with sources and timestamps" discipline §6.4/§6.5 already establish for red-flag conflicts, reused here for the same reason: a reviewer who has to go fetch the comparison will not.
2. **The reference asset's own provenance and freshness state** — when it was supplied, by whom, and whether it currently sits inside or outside its staleness window (§2) — using the same staleness machinery already built for every other fact class, not a new date-tracking mechanism.
3. **Which specific claim dimensions the reference actually grounds** — a reference photo may ground packaging (the box is shown) without grounding contents (the box was never opened in the photo), and the reviewer needs the tool to say so explicitly rather than assume total coverage from a single reference image.
4. **The generation mode actually used — reference-grounded versus plain generative** — surfaced the same way a requested-versus-delivered route mismatch is already surfaced (§5.6), so a silent fallback to ungrounded generation (a model substitution, a route degrade during the video pipeline's own fallback ladder) is visible before approval, not only discoverable in the ledger afterward.

**Interaction with §11.4's invalidation rule, ruled on explicitly.** §11.4 already invalidates every prior approve decision, and separately the AI-label acknowledgement, on any amendment, regenerate or re-assembly that changes an asset's packed bytes — stated there because a re-assembly can move, shrink or drop the burned-in disclosure, and an acknowledgement of a label that is no longer present is worse than none. **The depiction attestation is invalidated on the identical trigger, for a stronger version of the same reason.** A bytes change on a flagged asset can do worse than move a label: it can swap the depicted subject entirely — exactly the case §4(b) names, an accepted grounded keyframe replaced by a different, ungrounded one during a repair cycle. An attestation of "I compared image X against reference Y" is not merely stale after such a change, it may be describing an image that no longer exists in the pack at all. The depiction attestation is therefore fingerprinted and invalidated by the same mechanism §11.4 already uses for the AI-label acknowledgement — keyed to the packed bytes' fingerprint, which for a media asset already covers the mastered export together with its composed overlay set (§11.4) — with no separate rule needed. This is an extension of an existing rule to a new field the same rule already reaches by its own logic, not a new invalidation mechanism.

## 9. The fail-closed precondition

**An asset flagged as depicting a real sellable item, under Policy B, with no linked reference in its provenance record, cannot reach the review package as a publish candidate at all.** This is a new precondition alongside the two that already gate publish-readiness on provenance-record state: the AI-label-required flag (§7.7) and general provenance-record completeness (§14.6, §12.2). It degrades the asset to **plan-only**, never silently shipped and never blocked-forever — the same disposition §5.6 already uses for an asset whose renderer cannot be identified: the approved keyframe, script and prompt remain intact for a later run to complete once a reference exists, and the digest names the reason rather than presenting a gap. Under Policy A, this precondition has nothing to check, because no asset should ever be flagged as depicting a real item in the first place (§4); if one somehow is — a plan-time misclassification, a theme that has not opted in but whose brief nonetheless calls for a real-item shot — class 12 blocks it outright (§4) before this precondition is ever reached, which is the correct order: the policy-level block is upstream of the reference-completeness check, not a fallback to it.

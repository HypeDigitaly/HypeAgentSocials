# A1 — The Prohibited-Outcome Gate

**Status:** design-phase amendment, Amendment A (safety, pre-Stage-5), task A1. Binding architecture, not a proposal. No code is written by this document; its output is content the merge task (A4) inserts into `ARCHITECTURE_PLAN.md` per the wire-in table at §11.

**Closes:** P-10 — *"The claim ledger can launder an unlawful claim"* (`00_MASTERPLAN.md` §1). Every one of today's eleven check classes, and the twelfth (depicted-attribute) that task A2 adds alongside this one, asks a substantiation question — is this evidenced? A tenant who writes a true, honestly-sourced, permissioned testimonial into their own claim ledger passes every one of them. Some categories of claim are unlawful in the EU and in Czech law regardless of truth and regardless of evidence. This document specifies the control that catches that category, independent of the eleven/twelve check classes entirely.

**Severability.** This document is fully specified and fully enforceable with zero playbooks defined. Nothing below depends on the playbook layer, the pack registry, relation types, archetypes, angles, genres, CTA vocabulary, trigger lanes, node overlays, ranking profiles, or the config surface — all of which belong to Amendment B and none of which this document touches. Where the Gate's eventual relationship to a future pack registry matters, that relationship is stated as a **deferred extension**, never as a precondition for the Gate working today.

## 1. What the Gate is, and why it cannot be a claim check

Every check class in the claim-safety substrate — the eleven the architecture already runs (§6.7), and the twelfth (depicted-attribute) A2 adds — asks the same shape of question: *is there a ledger entry, a proof record, a resolved fact that this specific claim maps to?* That is exactly the right test for a claim that is lawful if true and evidenced. It is the wrong test, structurally, for a narrow but real category of claim that EU and Czech law make unlawful **regardless of truth, regardless of evidence, and in some cases regardless of any authorisation state a small operator could realistically hold**. A well-evidenced claim in this category is not a hard case for the eleven/twelve classes to get right; it is invisible to them, because the thing that makes the claim unlawful is not a missing fact.

Five instruments carry this property, at the confidence levels the evidence base honestly supports. None of these has been independently re-verified against primary EUR-Lex text this cycle; each carries the same confidence grading and the same counsel dependency it carried when first raised, and none of that is upgraded here. A Medium-confidence citation is stated as Medium confidence, not promoted to a settled fact because the argument built on it is important — the argument is warranted regardless of how the citation lands, which is the entire posture this section is written to preserve.

|---|---|---|---|

A true, well-evidenced claim not on the list is still unlawful. Evidence proves the claim is true; it does not, and cannot, prove the claim is authorised — and no fact class in this architecture represents "authorised" as distinct from "evidenced" | Medium (the closed-list *mechanism* is corroborated Medium-High by a directly-fetched EU Commission page; the Art. 10 number itself is not independently re-verified) | OD-L1 |

**The worked example that shows why substantiation-shaped checking cannot see this.** Take the claim "our sessions relieve anxiety." If the tenant has a genuine, honestly obtained, permissioned testimonial in the ledger, that claim passes check class 4 (outcome/result — ledger-backed), check class 9 (endorsement — permissioned), and every spin criterion S-1 through S-7 (§6.10), because the *pairing* is honest and the *evidence* is real. Nothing in the eleven check classes, run correctly and run in good faith, produces anything other than VERIFIED. **The defect is not that the system fails to check. It is that the system checks the wrong thing.** A claim can be perfectly substantiated and still be an unauthorised, unlawful therapeutic-outcome assertion under every instrument in the table above. A control built by densifying the eleven check classes — a bigger lexicon, a lower match threshold, an extra ledger field — cannot close this, because the defect is not in how hard the classes look; it is in what question they are built to ask. This is why the Gate is specified as a wholly separate control rather than as a twelfth (or thirteenth) check class, and why §6.7's own extension for this amendment does no more than record, in one sentence, that the Gate sits outside its table (§11 below).

## 2. Contents of the Gate

**Deterministic first, semantic second — the same ordering principle §6.7 already establishes for the eleven/twelve check classes, reused rather than reinvented.** A dictionary-and-pattern pass runs first: a list of condition and dysfunction nouns (recognised diseases and disorders, plus their common Czech colloquial and folk-medicine equivalents, authored separately per language per the same rule §6.7/§14.4 already state for every other Czech lexicon — a translated list both under- and over-blocks) cross-referenced against a list of outcome verbs and verb-equivalents implying treatment, cure, prevention, relief, healing or diagnosis, attributed to the tenant's own offer, service, product, session or practice. A model-driven semantic pass then catches paraphrase the dictionary pass structurally cannot reach — "your worries melt away" implies anxiety relief with zero lexical overlap against either list.

**Two states, and exactly two: `clear` and `prohibited-pattern-matched`.** The Gate does not use the eleven/twelve check classes' five-verdict vocabulary (VERIFIED / SAFE-NON-CLAIM / UNSUPPORTED / CONTRADICTED / DISCLOSURE-MISSING), and in particular **there is no VERIFIED state**, deliberately. VERIFIED, in the eleven/twelve-class vocabulary, means a ledger lookup succeeded — the claim maps to an entry the system trusts. Nothing in §1 of this document produces a state where that lookup could ever mean "and therefore lawful," because nothing in these five instruments is cured by evidence. A Gate with a VERIFIED state would be a Gate that implies a path to authorisation exists inside this system. None does. Adding a third state here would not add expressiveness; it would misstate the legal posture the Gate exists to hold, which is exactly the failure P-10 already demonstrates in the eleven-class substrate.

**Scope today, and the deferred extension.** With zero playbooks defined, the Gate ships with one engine-owned base pattern list, applied identically to every tenant and every theme. Annex `02_legal_claim_packs.md` §1.3 describes a future health & wellness pack that *densifies* this list — more condition/outcome pairs, a lower semantic-match threshold — for tenants whose vertical carries structurally higher exposure. That densification is real, useful, and entirely an Amendment B concern: it requires the pack registry and the playbook-selection mechanism this document does not assume exists. Nothing about the Gate's engine-floor behaviour changes when that registry arrives — a future playbook may only add entries to the pattern list (§5 states why), so the base list specified here remains the floor underneath any later densification, not a placeholder for it.

**A model-call node this control did not have before.** The semantic pass is a bounded language-model node in the sense §1.5 already defines the term — narrow input (one candidate span plus the two dictionaries' negative space), narrow output (`clear` / `prohibited-pattern-matched` plus, on a match, the matched span and the paraphrase reasoning), no internal iteration, a named behaviour when it cannot run (§7). It is not the same node as N-10 (the eleven/twelve-class semantic pass), because N-10's output shape is the five-verdict vocabulary against ledger entries in scope, and conflating the two nodes would blur exactly the boundary §2's "no VERIFIED state" rule exists to hold. This is therefore a fourteenth node in §1.5's inventory, alongside a fourteenth per-call token ceiling in §5.4a's aggregate. This document does not assign it a node number: node-identifier assignment is a merge-time, single-owner action in every other namespace this programme uses (`00_MASTERPLAN.md` §4 ruling C-5), and A1 authored in isolation is the wrong place to claim a number Amendment B's own work might reach for first. A4 assigns it at merge.

## 3. Position in the gate order — the single ownership statement

`ARCHITECTURE_PLAN.md` §14's introductory chain diagram is, by its own binding statement, **the sole owner of the per-asset gate chain** (D-21): "where any other section's ordering appears to contradict this one, this one governs." §6.10 explicitly disclaims ownership of the same diagram for the same reason — a chain drawn in two places becomes two different chains, and this architecture has already paid once for that mistake. Any statement of where the Gate sits in the chain is therefore, correctly, a statement about §14's diagram and nothing else. This section is that statement, made once, so that A2 (which needs to know where check class 12 sits relative to the Gate) and A4 (which performs the actual insertion into §14) can both cite it without restating it.

**The Gate runs at every point the claim gate itself runs**, for the reason §6.7/§6.10 already give for the claim gate's own double pass: a rewriting step anywhere downstream can reintroduce the pattern, and any gate that runs before a rewriting step must be re-run after it. Concretely, that means the Gate runs immediately before claim gate pass 1, immediately before claim gate pass 2 (including every re-entry of pass 2 that the combined-ceiling repair loop at §14 produces — the voice gate and the spin post-check are rewriting steps, so the Gate's own guarantee at pass 2 must hold on every lap, not only the first), and a third time at the post-assembly overlay claim pass, for exactly the reason that pass exists at all: for a media asset, claim-bearing text is composed at assembly, after text-side claim pass 2 has already closed, and the Gate's coverage of that surface cannot be weaker than the eleven/twelve deterministic classes' own coverage of it.

**The critical property is the ordering relative to the ledger, not relative to the other gates.** Within every one of the three passes above, the Gate's check completes **before check class 4 (outcome/result) ever performs its own ledger lookup**. A matched pattern short-circuits the pipeline before the substantiation question is asked at all — there is no code path, in any pass, by which a ledger entry is consulted for a Gate-matched span. This is the literal, architectural answer to "a tenant ledger entry must be unable to authorise this": authorisation is never queried, because the Gate never asks a question a ledger entry could answer.

This ordering statement — the three-pass placement, and the before-any-ledger-lookup property within each pass — is stated here once, is the version A4 inserts into §14's diagram, and governs over any other document's restatement of it, including annex `02_legal_claim_packs.md` §2.3's own diagram, which this document supersedes for the purpose of the merge. (One correction from that diagram: annex 02's wire-in table at its own §7 names §6.10 as where the diagram is added. That is incorrect against the current architecture — §6.10 explicitly does not own the chain, §14 does, per D-21, and §6.10 says so in its own text. §11 below wire-in table corrects the location.)

## 4. Mode-invariance

**The Gate is not mode-sensitive at all.** It applies identically in test, interactive and unattended modes, with no relaxation available to any of them. This is a deliberate departure from the one other place in this architecture where a safety-shaped trigger *is* mode-sensitive: §6.5's confidence-band degrade trigger is interactive-relaxable — an operator running interactively may knowingly accept a MINIMAL outcome from an offline snapshot older than the configured maximum window, a choice §6.5 and §6.6 both name as available only outside unattended runs.

The two triggers look superficially similar — both are named fail-closed behaviours, both name a specific condition, both are documented in the same section family (§11.3) — and the difference between them has to be stated rather than assumed. §6.5's trigger protects against **a data-freshness risk**: the brand facts might have changed since the snapshot was taken, and a human who reads the panel, sees the snapshot's age and the specific facts at risk, and decides the exposure is acceptable for this run is making an informed, bounded, reversible choice about *this run's data*. The Prohibited-Outcome Gate protects against **a strict-liability-adjacent legal exposure**: per §1, several of the underlying instruments make the claim category unlawful independent of the operator's belief about it, independent of evidence, and in one case (Dir. 2001/83/EC) with a consequence that reaches the product's own regulatory status rather than merely the advertisement. There is no informed-acceptance state available here, because there is no fact an operator could review that would make the claim lawful — accepting the risk "knowingly" changes nothing about whether the claim is unlawful, unlike accepting a stale snapshot, which genuinely does bound and disclose the actual risk being taken. A control whose entire value is that it cannot be reasoned around by a well-intentioned human under deadline pressure has to say so structurally, not rely on the human's judgement in the moment — which is the same argument §1.5 makes for why fail-closed points in general must be guaranteed to execute rather than left to an agentic model's discretion.

## 5. Why ledger, playbook and operator authorisation all lack a verb to reach it

Three separate mechanisms, each closing off a different party's route to relaxing the Gate, stated as three separate arguments because a single "nothing can turn it off" sentence would hide that each closure works for a different structural reason.

**1. A ledger entry cannot authorise it, because the Gate never performs a query a ledger entry could answer.** §3's ordering property is the whole of this argument: the Gate's check completes before class 4's lookup runs, in every pass. This is the same asymmetry §6.4 already states for the site-versus-claim-ledger relationship — "the site can subtract but never add," because the system must never let its own marketing copy bootstrap itself into approved truth — taken one step further. There, a source *can* be asked and its answer is constrained (subtract, never add). Here, nothing is ever asked. A ledger entry with a genuine, permissioned, well-sourced evidence pointer is not overridden by the Gate; it is never consulted, because the pipeline has already moved past the point where consulting it would matter.

**2. No configuration surface — today's theme configuration, or any future playbook layer — carries a verb that reaches the Gate at all, let alone one that could loosen it.** The Gate is not a member of the base pack or of any vertical pack (annex `02` §1.2 states this explicitly: "selected by nothing and disabled by nothing"), so the question "which pack turns this off" has no answer, because the Gate is not addressed by pack selection in the first place. This holds with zero playbooks defined, which is the point: there is currently no playbook layer to even attempt a relaxation, and every configuration surface this architecture does define today — the hard-excludes list (F-J), the AI-content class (§3.3) — is already built on the rule stated plainly at §6.3: **"Configuration may only tighten, never relax... a control that any tenant can weaken is not a control."** Every verb this architecture's configuration vocabulary defines is additive (add an exclude, add a lexicon entry, add a disclosure requirement); none is subtractive. When Amendment B's playbook layer exists, a playbook may extend the Gate's base pattern list exactly as a theme may add hard excludes today (§2's deferred-extension note); the playbook API surface, per the same inherited rule, has no verb named "narrow," "disable," or "exempt," and none is added by this document or should be added by any future one without reopening this section.

**3. An operator override cannot authorise it, because the bounded-override list is enumerated and this is not on it.** §6.4 already establishes that human run overrides are **bounded, not supreme**: an override may narrow — force a topic, suppress an offer, restrict to one language, lower the confidence ceiling — and may not create commercial facts, stated explicitly as "no new price, claim, client name, case metric or capability, absolutely, in unattended mode." This document extends that same enumerated boundary in the one direction it does not yet cover: an override may narrow a run's scope, but **may not create a therapeutic, medicinal, curative, preventive or diagnostic outcome assertion, in interactive or unattended mode alike**. Interactively as much as unattended — this is the one place this document's mode-invariance rule (§4) and the override-boundary rule meet, and both point the same way. The human review gate (§11.4) can approve or reject anything the pipeline produces, but it has nothing to approve here: a Gate-matched span never survives to a form the review gate could see it in, because the Gate's own enforcement ladder (§6) never ships it.

## 6. Enforcement, the drop terminal, and the exception this registers in §14.0

**The ladder deliberately diverges from the eleven/twelve-class ladder**, because the eleven/twelve-class ladder's middle rung — downgrade-repair, emitting the claim-free variant with proof stripped and the CTA softened — repairs the wrong defect here. Downgrade-repair works when the problem is *missing evidentiary support for an otherwise fine assertion*. The Gate's match is not that; the defect is the assertion's *shape*, and a version of "our sessions relieve anxiety" with the ledger reference removed is not safer, it is the same unlawful claim with its evidence trail deleted.

1. **Bounded regenerate is permitted**, fed a positive constraint — remove the disease/condition-outcome framing entirely, describe the practice rather than its effect on a named condition — using the **same mechanics and the same per-pack claim-retry budget as the existing eleven/twelve-class ladder** (§6.7, named at §4.9 as one of the four distinct regeneration counters this architecture tracks). The Gate does not get a fifth counter. This is a deliberate choice, not an oversight: inventing a separate budget for the Gate would silently make §4.9's "four distinct regeneration budgets, named so no section can refer to 'the regenerate cap' ambiguously again" false the moment this document merged, and a document whose own subject is closing a defect caused by an unstated interaction should not open a new one.
2. **There is no downgrade-repair step.** On exhaustion of the regenerate allowance, the asset is **dropped**, not shipped in any softened or claim-free form, with the reason recorded and the rejected draft attached — the same never-silently-ship, never-silently-discard-without-a-note discipline §6.7 already states for every other gate's terminal.
3. **Logged per asset**, the same regulatory-defensibility discipline §6.7's per-asset claim-check log already provides generally.

**The conflict with §14.0, stated precisely.** §14.0 governs the combined per-artifact repair ceiling across every gate that can cause a rewrite, and its exhaustion rule is exact: *"If [the combined ceiling] is exhausted, no further repair of that artifact is attempted by any gate: the artifact takes the downgrade-repair variant if one exists for the failing gate, and otherwise enters the pack labelled with the gate it could not clear."* Neither branch of that sentence is available to the Gate. It has no downgrade-repair variant (point 2 above states why one would be actively unsafe, not merely absent). And "enters the pack labelled with the gate it could not clear" is not a safe fallback here the way it is for, say, an unpassed voice gate: a voice-labelled asset ships prose that failed a *quality* bar, visible to a reviewer who can still reject it on sight. An asset labelled "did not clear the Prohibited-Outcome Gate" and packed anyway would ship the literal prohibited assertion into the review package — the harm the Gate exists to prevent has already occurred the moment that text exists in a form a human, or a downstream automated re-composition, can read and reuse. §14.0 as currently written does not contemplate a gate whose failure mode makes both of its own listed exhaustion outcomes unsafe, because every other gate it governs (spin, claim, voice) has at least one.

**Resolution: a named exception is registered inside §14.0's exhaustion rule for the Gate, rather than giving the Gate a separate repair allowance outside the combined ceiling.** The rule's first sentence is read, and is to be written by A4, as: *"...and otherwise enters the pack labelled with the gate it could not clear — except where the failing gate is the Prohibited-Outcome Gate, which has neither a downgrade-repair variant nor a safe labelled-and-packed state (§6 above), and whose exhaustion instead drops the artifact, with the reason recorded and the rejected draft attached, per its own enforcement ladder."*

This is chosen over giving the Gate its own allowance outside the combined per-artifact ceiling and the per-pack claim-retry budget, for two reasons. First, the Gate's own enforcement ladder (point 1 above) already states that its bounded regenerate draws on the *same* per-pack claim-retry budget the eleven/twelve classes use — an allowance "outside" that budget would contradict this document's own §6 in the same breath it was proposed, and would recreate exactly the kind of unstated cross-gate interaction §14.0 exists to prevent in the first place: two gates, each individually within its own budget, able to ping-pong an artifact between them indefinitely. Second, "it is not a claim check" is true and is the reason the Gate's verdict vocabulary and its middle rung differ from the eleven/twelve classes' (§2, §6 points 1–2); it is not a reason to exempt the Gate from the combined-ceiling *accounting*, which exists to bound worst-case repair cost per artifact regardless of which gate is doing the repairing. The exception belongs at the narrowest point that is actually broken — the exhaustion *outcome*, not the exhaustion *counting* — which is what a named exception inside the existing rule delivers and a parallel budget would not.

**The interaction with the combined per-artifact ceiling, stated explicitly in both directions, because §14.0 governs exactly this and an unstated interaction here would itself be a defect of the amendment:**

- A Gate regenerate on an artifact counts toward that artifact's combined per-artifact ceiling exactly as a spin, claim-pass-1, voice, or claim-pass-2 regenerate does. An artifact that has already spent most of its combined ceiling on voice-gate rewrites has correspondingly less headroom left if the Gate later matches on that same artifact — it does not get a fresh ceiling because the triggering gate changed.
- A Gate regenerate draws on the pack's claim-retry budget exactly as an ordinary check-class regenerate does. A pack whose claim-retry budget is already exhausted by ordinary check-class repairs, at the point the Gate first matches, has zero regenerate attempts left for the Gate and proceeds straight to drop for that artifact — this is a real, sometimes-adverse interaction, and it is deliberately accepted rather than hidden: a pack burning its claim-retry budget on ordinary repairs is itself informative (per-pack budgets are checked at §14.0 rule 2, ahead of per-artifact counters at rule 3, and their exhaustion already degrades the whole pack to review-required), and a Gate that got a protected, unshared budget merely to avoid this interaction would be quietly weaker in the one case — a pack already showing repair strain — where the operator most needs a legible, honest degrade rather than a gate that always finds a way to try once more.

## 7. Fail-closed behaviour on the Gate's own unavailability

This is an application of §11.3's existing fifth fail-closed trigger — *"a gate that cannot execute"* — not a new sixth trigger class. §11.3 already states the general rule and a per-gate list of named degraded outcomes for every gate this property applies to; this document adds the Gate's entry to that list rather than arguing for a new category of trigger.

The deterministic dictionary pass is a local pattern match and should almost never itself be unavailable — it has no external dependency and no model call. The semantic paraphrase pass (§2's fourteenth node) is a model call and can fail exactly as any other model node can: timeout, outage, unparseable output, a budget ceiling reached mid-pass. On that failure, **the Gate degrades to deterministic-only verdicts, and treats anything ambiguous as a match, never as clear.** This is the same fail-closed direction §11.3 already states for the eleven/twelve-class claim gate's own semantic pass ("Claim gate semantic pass unavailable → deterministic verdicts only, and every claim-shaped candidate is blocked rather than passed"), applied to a control whose two-state vocabulary makes the rule simpler to state, not different in kind: an asset the Gate cannot fully evaluate does not ship un-evaluated, and where the deterministic pass alone cannot resolve a span with confidence, that span is treated as matched, never as clear, because clear is the state that lets an asset through and this is exactly the direction a safety gate must never fail in.

## 8. The escalating digest event

A repeated Gate trip on the same topic/offer pairing is surfaced as its own named digest event, **distinct from an ordinary regeneration count**, because it says something about the offer's positioning, not about prompt quality. An artifact that trips the Gate once, gets a clean regenerate, and ships tells the operator nothing beyond "the drafting model reached for a metaphor once." An offer that keeps producing Gate-matched drafts across multiple runs is telling the operator something true about how that offer is being framed at the brief level, upstream of any individual draft — and folding that signal into the ordinary claim-retry-budget exhaustion message, or into a per-asset attempt count nobody reads across runs, would bury exactly the finding this control is best positioned to surface.

This reuses the anti-flap escalation mechanism §8.12 already owns for repeated degrades, rather than inventing a second one: the existing mechanism escalates prominence on repetition instead of repeating an identical low-signal message, currently keyed on source health and on degrade type. This document adds a third key: the **(topic identifier × offer identifier) pairing**, tracked across runs, not reset per pack. A single trip in a run is logged per asset as usual and need not appear at digest-header prominence. A second trip on the same pairing raises a named line in the run digest (§12.1's digest anatomy) reading approximately "this offer's messaging keeps needing therapeutic-outcome framing removed" — worded to name the offer's positioning, not the model's behaviour — and a further repeat escalates prominence again rather than repeating the same sentence, exactly as every other anti-flap escalation in this architecture already behaves.

## 9. The licensed-clinic limitation, stated honestly

A genuinely licensed clinic — a lawfully authorised health-claim advertiser — is a real case, and the honest v1 answer is that **this system cannot safely serve that tenant's regulated-claim content at all**, for reasons that are not a missing configuration knob and would not be fixed by one.

There is no fact class today, and none proposed by this amendment, that could represent "this tenant holds a current, scope-limited professional licence entitling them to make regulated therapeutic claims about condition X." Building one requires deciding, ahead of any engineering, what counts as evidence of licensure — a national medical or psychotherapy register entry, a specific professional chamber's confirmation — who verifies it, and how often it is rechecked. That is a genuine product-plus-legal design task, not a data-entry field, and it is not attempted here.

Even a verified licence would not uniformly unlock the Gate, because licensure interacts differently with each of §1's five instruments. A licensed Czech psychotherapist may be entitled, under their own profession's advertising rules — an unresearched body of Czech law, carried forward as OD-L7 — to describe their *service* in clinical language. That entitlement does nothing to authorise a *food or wellness product* claim under Reg. 1924/2006, which runs its own separate, EU-level authorisation procedure that a national professional licence does not satisfy. A single "licensed: yes/no" flag would therefore be worse than useless — it would let one licence unlock a claim class it has no bearing on.

Designing a licence-verification and per-instrument authorisation-state model without qualified regulatory-affairs counsel input would itself be exactly the kind of unlawful-claim-laundering risk P-10 already demonstrates, applied one layer up: the system inventing its own compliance apparatus in place of a genuine legal answer, and dressing that invention in the appearance of a control. A licence-verification feature built to this standard would not reduce the Gate's exposure; it would create a new, false sense that the exposure had been handled, which is a worse position than the honest gap this section states.

**The v1 answer is therefore explicit and deliberately unautomated: a genuinely licensed tenant's regulated-claim content is authored and reviewed entirely outside the claim-ledger/claim-gate substrate, by the operator, by hand.** This is the same posture this architecture already takes toward the things it has decided it cannot safely automate — the guaranteed rung-3 local-staging floor, the manual AI-label acknowledgement (§14.6) — applied to a case where the "cannot safely automate" judgement rests on legal rather than technical grounds. Whether a licensed-claims pathway should exist in a later version, and what it would need to evidence per instrument, is carried forward as **OD-L8** rather than designed now, exactly as annex `02` §2.6 already states it: build this only if and when a licensed-clinical tenant is actually onboarded, jointly with qualified counsel, and not before.

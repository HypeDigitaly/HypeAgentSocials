# 06B — The resolver

*Design-phase annex to `CONDUCTOR_RULINGS.md` (binding: CR-1, CR-2, CR-3, CR-4, CR-7, CR-8) · companion to `06C_authoring_form.md`, which owns the field shapes this document resolves against · prose and tables only, no code, no pseudocode, no configuration syntax*

The operator asked for a form that is "super simple — ideally just to write text prompt instructions into the fields for guidance or use arrays with values" (`CONDUCTOR_RULINGS.md`, preamble). `06C_authoring_form.md` designed that form: twelve Tier-A fields and three Tier-B fields, most of them closed picks or literal arrays, a small number of them free-text guidance. This document designs the machine that stands between that form and the pipeline: **the resolver**. CR-1 names it; CR-2, CR-3, CR-4, CR-7 and CR-8 bind its behaviour; nothing here relaxes any of the five.

---

## 1. The resolver's contract

### 1.1 Inputs, exactly

| Input class | Source | Nature |
|---|---|---|
| **The authoring form** | `06C_authoring_form.md` Tier A (Fields 1–12) and Tier B (B1–B3) for one theme | Closed picks (Fields 5, 6, 9's CTA-type column), literal arrays (Fields 4, 7, 8, 9's destination column, B2's explicit table), and bounded free-text guidance (Field 10 the brief; B1's mix sentence; B2's optional steering sentence; B3's optional custom-voice paragraph) |
| **Engine registries, at their pinned versions** | Objective (5) · relation types · post archetypes (11) · angle taxonomy (15) · voice genre (6) · CTA vocabulary (10–11, see §2.6) · criterion families and bars · fact-class taxonomy and obligation vocabulary · ranking-profile set · per-source query capability table (`05_query_steering.md` §2) | Read live at resolution time, never hard-coded into the resolver's own logic — see §2.6 for why this matters |
| **Existing theme facts** | The theme's prior resolved config, if one exists (for diffing, §3) · the fingerprint of the last accepted resolution · the brand-truth pointers already on file (Field 2) for the fact-schema substitution check (§2.5) | Read-only inputs; the resolver never writes brand truth |

### 1.2 Outputs, exactly

| Output | Contents |
|---|---|
| **The resolved form** | Registry-member identities (one content objective, the relation-type set, archetype eligibility and mix weights, angle enable/weight table, voice genre, CTA-class enablement, fact-schema obligation levels and any substitute classes, criterion-family activation pattern, ranking-profile assignment per language × trigger class, per-source query field values) — every one version-pinned to the registry it was drawn from |
| **The bounded brief** | The single free-text field (CR-8), carried near-verbatim, never registry-mapped (§5) |
| **The literal arrays** | Watch topics with per-language surface forms, hard excludes, CTA destinations, per-source query overrides — validated and normalised, never rewritten (CR-4) |
| **The readback** | Plain-language, per CR-2 property 2 (§3) |
| **The diff**, on re-resolution | Impact-ordered, per CR-2 property 3 (§3) |
| **The failure report**, when resolution cannot complete | Named field, quoted span, reason, disposition (§4) |
| **The overlay fingerprint contribution** | The resolved form's digest, folded into the per-node overlay fingerprint per §4.4 of `03_pipeline_and_gates.md` |

### 1.3 What the resolver is not

The resolver is **not a pipeline node, does not become N-14, and sits outside per-run budgeting, per-run latency and per-run idempotency** (CR-2). Three sentences justify the boundary. First, cadence: the thirteen nodes process one run's candidates and artifacts every time a run happens; the resolver processes one theme's authoring form only when that form is edited — a categorically different trigger, and conflating the two would make a run's cost non-computable before it starts, which is exactly the property `03_pipeline_and_gates.md` §1.5 invariant 5 exists to guarantee. Second, precedent: `04_RECONCILIATION.md`'s ruling C-1 already established that the node inventory stays at thirteen when a genuinely new checking function (N-8) turned out to already exist inside it — the resolver is the inverse case, a genuinely new *function* that does not belong inside the inventory at all, because it has no per-run input, no per-artifact output and no gate disposition of its own. Third, safety: if the resolver ran per candidate or per artifact, operator prose would be re-interpreted on every run, reopening exactly the "free prompt reaching a gate" failure mode CR-3 exists to close — running it once, at load, and freezing its output into a versioned, fingerprinted, literal resolved form is what makes CR-3's guarantee ("gates receive none. Ever.") hold at runtime.

### 1.4 Where it sits

The resolver is one step in a four-step load-time sequence, and the order is deliberate — cheap, structural checks run before expensive, semantic ones, so a misconfigured theme fails fast rather than burning eval-set tokens on a form that was never going to resolve.

| Step | What runs | Trigger | Can block scheduling |
|---|---|---|---|
| 1 — **Resolve** | This document's subject: authoring form → resolved form, readback, diff | An edit to the authoring form (CR-2 property 1) | Yes — an unresolved field, per §4, keeps the whole config inert |
| 2 — **Accept** | The operator reads the readback (and any diff) and takes the accept action; a refusal banner (§3, §4 item 2) requires its own acknowledgement | Human action, no timeout | Yes — CR-2 property 2: "the resolved config is inert until the operator accepts it" |
| 3 — **Readiness validation** | The eleven-plus assertions of `03_pipeline_and_gates.md` §8 (registry resolution, archetype/destination eligibility, criterion coverage, fact-schema soundness, prompt-fit-to-ceiling, eval/golden-set pointers, etc.) — structural checks over the now-complete resolved form | Automatic, immediately after acceptance | Yes — the standing posture: "may still run interactively in test mode; may never be scheduled" |
| 4 — **Regression gate** | `03_pipeline_and_gates.md` §4.5: the engine frozen eval set (veto power) plus the playbook's own eval set, run against the new fingerprint | Automatic, on any fingerprint change, per `00_MASTERPLAN.md` Wave-1 review finding B1 ("the regression gate fires on any fingerprint change at any layer") | Yes — a regression is a precondition failure, not a warning |

Step 3 before step 4 is this document's recommendation, not a settled ruling — it is carried forward as **CFG-OD-10** (§8), because neither `CONDUCTOR_RULINGS.md` nor `03_pipeline_and_gates.md` states the order explicitly and the alternative has a real cost consequence.

## 2. The mapping problem, registry by registry

### 2.0 Two postures, and why the split matters

`06C_authoring_form.md`'s field design already did most of the safety work for this document, by making most fields **closed picks or literal arrays** rather than free prose. Reading the shipped form against the ten registries the task names, the resolver's actual work splits cleanly into two postures, and conflating them is the single easiest way to over-design this component.

**Posture A — cascade.** The input is already a closed selection (a pick from a short list, or the presence/absence of a structured entry). The resolver's job is table lookup plus **making the consequences visible**, because the operator picked one thing and several other registries silently followed. No interpretation occurs; nothing can be ambiguous in the CR-7 sense, because there is no free text to misread.

**Posture B — interpretation.** The input is genuinely free text, and the resolver must map it to a registry member or a literal value it did not previously have. This is the only posture where CR-7's ask-don't-guess rule has work to do, and it touches a deliberately small surface: the brief (excluded from registry-mapping entirely, see §5), the two Tier-B guidance sentences (B1, B2), the optional custom-voice paragraph (B3), the fact-schema substitution trigger buried in Field 2, and the per-source query composition gap in Field 4.

Every resolved value carries a **provenance tag**, and the tag *is* the override mechanism the operator has (CR-1 forbids a second enum surface, so there is no separate "override" control):

| Tag | Meaning | How the operator produces it |
|---|---|---|
| **Named** | The operator used a closed pick, or wrote the registry member's canonical name/a whitelisted synonym directly in prose | Ticking a box (Fields 5, 6, 9), or writing the term itself in a guidance field |
| **Inferred** | The resolver mapped free text to a registry member above the confidence floor | Writing descriptive prose that the resolver classifies with no competing signal |
| **Defaulted** | The operator wrote nothing for a field with a real default (Tier B, CR-5) | Leaving a Tier-B field untouched |
| **Refused** | The operator's text mapped to something the resolver will not apply | Writing guidance that implies a Tier-1 relaxation (§4 item 2) |

### 2.1 Table 2A — Cascade-resolved registries

| Registry | Cascade source | What the resolver does | Confidence |
|---|---|---|---|
| **Content objective (5)** | Field 5, an explicit pick of one of the five names in `06C` | Echoes the pick; states its downstream consequences (which criteria it emphasises, which CTA classes it permits, per `01_content_ontology.md` §1) in the readback, because the operator picked a label, not the consequence list | Always Named — there is no inference step |
| **Playbook kind → relation-type set** | Field 6, a pick from the (currently short, growing) closed list | Table lookup from playbook kind to its declared relation-type set (e.g., B2B-lead-generation → offer-attachment only; a reach-and-community kind → expressive-aesthetic plus commentary-observation) | Named for the pick; the *fan-out* is Defaulted-with-source, and the readback must say so explicitly (§3) |

| **Voice genre (6), default** | Derived from playbook kind | Sets the default genre; B3 may override by pick (Named) or by custom description (Posture B, §2.2) | Defaulted-with-source, overridable |
| **CTA-class enablement default** | Derived from playbook kind, then narrowed to exactly the classes for which Field 9 supplies a working destination | A class with no Field-9 entry is not enabled, regardless of what the playbook kind would otherwise permit — availability of a real destination is a harder constraint than genre fit | Named per class present in Field 9; Defaulted (to "not enabled") for classes absent |

| **Criterion *bar* strictness** | Not present in the shipped authoring form at all | The resolver applies the registered default bar and goes no further | Tier C by design (see box) |
| **Fact-schema obligation levels** (excluding substitution target) | Derived from content objective and playbook kind: which classes are mandatory-resolved, mandatory-resolved-or-legitimately-empty, constraining, enriching | Pure lookup against `03_pipeline_and_gates.md` §5.2's rule set | N/A |
| **Ranking profile per (language × trigger class)** | Field 3 (languages) crossed with whether a calendar-register or evergreen-library field exists in the authoring form | Today's shipped form (`06C`) carries **no** calendar or evergreen-library Tier-A/B fields, so every theme currently resolves to the Trend profile only, split counted/uncounted per language exactly as `03_pipeline_and_gates.md` §6.2 already does. This is a scope boundary of `06C`, not a resolver limitation — the day calendar/evergreen fields ship, this row gains a genuine Posture-A cascade (lane presence ⇒ Occasion/Library profile), still with no free-text inference | N/A while those fields are unshipped |

> **A deliberate design choice, stated rather than assumed.** Criterion bar strictness is the single highest-risk mapping this document could specify — it sits directly on the Tier-2 relaxation surface `00_MASTERPLAN.md` §3.1 names, and `06C_authoring_form.md`'s shipped field list, correctly, gives the operator no field to write "be stricter" or "be looser" into. This document recommends the resolver **never infer a bar change from prose in v1**: bar selection stays Tier C (CR-5) — reachable only through an explicit, logged expert override outside the authoring form, never through resolver interpretation of a guidance paragraph. The four moves `03_pipeline_and_gates.md` §3.1 permits a playbook (activate an optional criterion, choose a stricter bar, add an available criterion, nothing else) remain real, but this document proposes they are exercised by whoever builds a new playbook kind, not inferred per-tenant. This is recorded as an open decision, not a foregone one — **CFG-OD-11**, §8 — because a future revision of `06C` could add a Tier-B "extra scrutiny" field, and if it does, this document's confidence-floor discipline (§2.2) would need to apply to it with the elevated floor genre inference already gets.

### 2.2 Table 2B — Interpretation-resolved values

| Field | Free-text signal | Confident | Ambiguous → CR-7 disposition | Override / recording |

### 2.3 Voice genre — elevated floor, restated once

Voice genre appears in both tables because it has both a cascade default (§2.1, from playbook kind) and an interpretation path (§2.2, B3's custom description). The elevated confidence floor applies only to the interpretation path; the cascade default needs no floor because it is Named by construction. This is deliberate: `00_MASTERPLAN.md` §3.1 established that genre is the one registry where "bar values only, never dimensions" *fails as a containment argument*, because a polarity flip (curiosity-gap forbidden → rewarded) is a change in kind, not degree. A resolver that treated genre inference with the same confidence floor as, say, archetype-mix parsing would be applying a Tier-2-safe discipline to a Tier-2-*variable* registry — the one place in this whole design where "confident enough" and "safe enough" are not the same question.

### 2.4 CTA classes (10–11) — the registry that proves why the resolver must read live

`01_content_ontology.md` §6 tables eleven CTA-class rows (content, product-path, order/purchase, reserve/book, subscribe/join, visit/directions, follow/tag/save, share/comment/tag, engage-via-response, no-CTA, commercial-incentive). `CONDUCTOR_RULINGS.md`'s preamble says "ten classes." `00_MASTERPLAN.md` §0's own audit line records this exact miscount as a known defect ("'ten CTA classes' over an eleven-row table"). `06C_authoring_form.md`'s own "Contradictions Found" section rediscovers it independently and resolves it *for that document's purposes* by treating the eleven-row table as canonical while listing only ten items in its recount — dropping commercial-incentive without saying so.

This document does not resolve the count. It is not this document's registry to fix, and CR-1's whole design premise is that the resolver **never** holds a hard-coded count of anything — it reads the registry's live member list at resolution time (§1.1). The practical consequence: whatever the count turns out to be once `04_RECONCILIATION.md` (or its equivalent for this working track) settles it, the resolver's CTA-class row in §2.1 does not change in shape, only in the length of the list it iterates. This is the strongest available argument for why registry-liveness (rather than any document, including this one, asserting a fixed number) is the correct discipline.

## 3. The readback — the operator's only defence

Per CR-2 the resolved config is inert until accepted. The readback is what the operator accepts, so its shape *is* the safety control, not a report about one.

### 3.1 Contents and order

1. **Header.** Theme identity, resolver version, the registry versions referenced, resolution timestamp, the overlay-fingerprint value this resolution would produce if accepted.
2. **Attention-required summary, first, before anything else.** Three sub-blocks, each short and scannable, because these are the items most likely to be skimmed past in a long mirrored readback:
   - **Defaulted** — every field the operator did not touch that carries a real value anyway, with its source (engine floor / playbook-kind cascade / Tier-B default) named, per CR-5's discipline that no field may read "no default" silently.
   - **Said but not used** — every quoted span the resolver read and did not apply, with the reason. This is where a §4-item-2 Tier-1-relaxation refusal lives, permanently, every time the config is read back, not only at the moment of the attempted edit.
   - **Refused entirely** — any field that could not resolve at all (§4), which blocks acceptance outright and is not part of what can be accepted.
3. **Field-by-field body, in the authoring form's own field order (1–12, then B1–B3).** For every field: the operator's own text or pick, quoted verbatim; immediately followed by the resolved selection(s), each carrying its provenance tag (§2.0). This mirrors the order the operator wrote the form in, so the operator can trace their own document down the page rather than a reordered one.
4. **Literal arrays, verbatim.** Watch topics, hard excludes, CTA destinations, per-source query overrides — echoed exactly as authored, with only validation notes attached (e.g., "checked against ten sources; DataForSEO accepts this as `keyword`; TikTok does not accept keyword search — see `05_query_steering.md` §2.2"). CR-4 governs: nothing here is ever paraphrased.
5. **The brief, verbatim, with its measured length against its cap** (§5).
6. **The overlay fingerprint** this resolution would set, and which nodes' fingerprints it changes.
7. **The accept action.** A single acceptance covers items 3–6; any item in the "refused entirely" sub-block of item 2 requires its own separate, explicit acknowledgement before the *rest* of the config can be accepted — the operator cannot accept past a refusal without reading it, distinguishing "I reviewed this" from silently scrolling through it.

### 3.2 The diff on re-resolution — ordered by impact, not by edit size

The one property CR-2 names explicitly — "a one-word change in a guidance paragraph that silently flips a voice genre must be visible" — is a decorrelation problem: authoring-text edit size and resolved-form change impact are unrelated. A rewritten paragraph can leave every resolved selection unchanged; a single adjective can flip a Tier-2-variable registry. The diff is therefore organised by **impact of the resolved-form change**, never by size of the authoring-form edit:

| Block | Contents | Why it is separated |
|---|---|---|
| **High-impact changes** (always first, visually distinct) | Any change to: voice genre, relation-type set, fact-schema substitution target, CTA-class enablement, criterion-family activation pattern | These are the registries where a changed selection changes gate or judge behaviour downstream, per §2's Posture-A/B split — the operator must see these regardless of how the edit that caused them reads |
| **Routine changes** | Archetype mix weights, angle weights, array additions (a new watch topic, a new hard exclude), destination changes | Real changes, but ones whose consequence is bounded to volume/emphasis rather than to which safety-adjacent rule set is active |
| **No-op confirmations** | Fields whose authoring text changed but whose resolved value did not | Prevents the operator reading "nothing changed" as "I don't need to look," while still keeping it visually subordinate to the two blocks above |

For every high-impact entry, the diff shows not just the label change but the **calibration status** of the new selection (e.g., "creator-casual → evocative-expressive; golden set: present, flag-rate ceiling active" versus "→ a genre with an inactive flag-rate ceiling, judge runs deliberately lenient") — so the safety consequence, not merely the name, is what the operator is asked to accept.

### 3.3 Language

The operator works in both Czech and English. The readback is rendered **per field, in the language that field was authored in** — a theme with an English brief and a Czech watch-topics table gets an English readback sentence for the brief and a Czech one for the topics — rather than forcing one language for the whole document or duplicating everything bilingually. Two things never translate: **registry-member identifiers stay in their canonical, engine-defined form** (e.g., "evocative-expressive," "S-12 product accuracy") in every readback regardless of the surrounding language, because these are versioned, pinned identities (§4.4 of `03_pipeline_and_gates.md`) and a translation of the identifier itself is a second, uncontrolled place semantic drift could enter a safety-relevant selection — exactly the discipline §6.12 of `ARCHITECTURE_PLAN.md` already applies to facts ("the Czech voice lexicon... belongs to the language overlay; this layer only requires that fact and claim layers be per-language rather than translated"). The connective prose around an identifier translates; the identifier does not.

## 4. Failure taxonomy

Nine entries. **Fail-closed is the design throughout**, and every entry below defaults either to *refuse and ask* or to *refuse and keep the existing safe state* — never to a best-effort guess. Item 2 is the one entry that does not halt resolution, and it is defended as fail-closed rather than as an exception: it does not halt because its fallback (the floor stays exactly where it was) is already the safe state, so halting would add friction without adding safety. No entry in this taxonomy departs from fail-closed; §2.2's Virlo-`intent` templating comes closest to a genuine exception (the resolver does produce text that leaves the config surface) and is defended there on the grounds that the text is deterministically templated from literal content, never model-paraphrased, and its downstream failure mode (a zero-yield query) is already an existing, honestly-reported degrade (`03_pipeline_and_gates.md` §1.6's "zero candidates is correct" line), not a new safety surface.

| # | Failure | Trigger | Message shape | Blocks | Recoverable without new information |
|---|---|---|---|---|---|
| **1** | **Unmappable span** | Free text maps confidently to no registry member above the floor | Names the field, quotes the exact span, names the registry it was checked against, states "no member matched" — never a nearest-guess | The field; other fields may still show provisional resolution to aid the fix, but the config as a whole stays unaccepted | Yes — an editorial fix. *Escalation case:* if the unmappable span is Field 6 (Playbook Kind) itself, per `06C`'s own text ("the system will ask you to pick the closest one or create a custom playbook"), the resolver states explicitly that this may not be a configuration fix at all — a new playbook kind is "a project," not configuration (`00_MASTERPLAN.md` §8) |
| **2** | **Guidance implying a Tier-1 relaxation** | Text semantically requests waiving/loosening a PROOF, NEXT-STEP or GLUE-family criterion, a hard exclude, the disclosure floor, or any other engine-floor item | Quotes the span, names the specific floor by ID (e.g., "S-5 proof discipline — engine floor, `00_MASTERPLAN.md` §3.1, non-waivable"), states the instruction was not applied | Nothing — resolution continues with the floor intact; the refusal is recorded permanently in the readback's "said but not used" block (§3.1 item 2) and requires its own acknowledgement before the config as a whole can be accepted | Yes, trivially — the floor already holds; no operator action is required to reach a safe state, only to acknowledge it |
| **3** | **Internally contradictory guidance** | Two clauses imply mutually exclusive registry selections with no stated primary | Quotes both spans, names both candidate members, asks which is primary — but first checks whether the apparent contradiction is actually a valid per-archetype secondary genre declaration (`01_content_ontology.md` §5, rule 3: "our lead-gen playbook has a BTS content stream; BTS assets are judged against sensory-hospitality genre") before flagging it as a true contradiction | The field | Yes — disambiguation |
| **4** | **Guidance that would empty a mandatory fact class** | A substitution declaration (Field 2) names no checkable resolution source anywhere in the form for a class the resolved relation-type set still requires; or guidance implies removing a class from the universal mandatory core (identity, audience map, hard excludes, compliance — never touchable, `03_pipeline_and_gates.md` §5.2 Rule 1) | Quotes the span, names the fact class, states which rule is unmet (Rule 1 untouchable, or Rule 5 non-triviality — no external verifier and no dated attestation for a class where attestation alone does not suffice per C-4) and what would satisfy it | The whole config — an unresolved mandatory class fails the theme to INSUFFICIENT (`03_pipeline_and_gates.md` §5.3) and no resolved config may ship in that state | No — needs new information from the operator (a checkable source), not merely a rewrite |
| **5** | **Brief exceeding its cap** | The brief's measured length, post-tokenisation, exceeds the cap computed from §4.7's reserved-first allocation (§5.3) | Names the field, states the cap and the measured length, quotes the specific trailing content pushing it over | The whole config — the brief is load-bearing for multiple nodes and cannot ship partially | Yes — shortening, no new information needed |
| **6** | **Brief containing numeric or proof-shaped content** | A deterministic lexical/pattern scan matches (§5.2) | Quotes the exact offending span, per CR-8's own wording: "rejected at load with that span quoted back" | The whole config, same reasoning as #5 | Yes — removal or rephrasing |
| **7** | **Array member matching nothing on any source** | A literal array entry (a watch-topic surface form, a CTA class name, a destination, an angle name in B2's explicit table) fails validation against the live registry/source-capability check | Quotes the exact entry, names the array field, states what it was checked against and that nothing matched — distinguishes an **editorial fix** (a typo, a class name that doesn't exist) from an **engineering ask** (the entry names something that would require a new registry member or a new source, which is out of the resolver's power to grant) | That field's config surface, until fixed or withdrawn | Usually yes (typo); sometimes no (a genuine new-capability request, which the resolver names as such rather than silently dropping the entry) |

## 5. The brief — the one free-text field that survives compilation

### 5.1 Permitted and forbidden content

The brief (Field 10, `06C_authoring_form.md`) is **style-and-emphasis guidance for generation nodes, never a fact channel** — the exact discipline `ARCHITECTURE_PLAN.md` §6.11/D-15 applies to the exemplar corpus ("the exemplar corpus is style-only and never a fact source"), extended to operator-authored text for the same reason: whatever the brief says about the world is not treated as evidence by any downstream gate. Permitted: tone and register reminders, thematic emphasis, what to notice or avoid noticing, non-numeric context about what the brand is or is not. Forbidden, per CR-8 verbatim: "a number, a client name or a results claim." This document reads "proof-shaped" broadly, matching `ARCHITECTURE_PLAN.md` §6.11's own list — efficacy claims, comparative claims, endorsement claims, superlative claims — because the corpus-leakage hazard §6.11 names ("the generator is being shown these numbers as examples of good writing at the exact moment it writes") applies identically to a brief.

### 5.2 Deterministic enforcement, and its honest limit

The scan is a **deterministic lexical/pattern check**, not a judgment-model call, and this is stated because the task requires it to be: digit-shaped tokens, currency symbols, percentage signs, a bounded superlative/comparative lexicon ("best," "#1," "guaranteed," "voted," "proven"), a bounded endorsement lexicon (third-party validation phrasing), and — per `06C_authoring_form.md`'s own **CFG-OD-4** recommendation, which this document adopts and operationalises — competitor names checked against the hard-excludes array (Field 8), client names checked against the proof allowlist, and metric-shaped number-plus-outcome pairs. This check does **not** require a judgment model to enforce the fail-closed floor at load time, and the design is deliberately biased toward false positives: an entry it is unsure about is rejected, never passed.

The honest limit: a purely lexical scan has a residual false-negative rate against stylistically-disguised claims that carry no digit and no lexicon hit at all ("everyone who tries us stays," "the only real option"). This document's conclusion is that closing that residual gap **does** require a judgment model, and states the consequence plainly: such a pass must never become the load-bearing gate, because a model-mediated check at the resolver's own load-time boundary would reopen the exact transitive-influence question §6 addresses, one layer earlier. If added at all, it is strictly **advisory** — logged, non-blocking, never itself capable of failing or passing the config — and the deterministic scan remains the sole fail-closed floor. This is carried forward as **CFG-OD-9** (§8) rather than decided here, because whether the residual gap is worth the added surface is an evidence question the Phase-0 trial, not this document, should answer.

### 5.3 Length cap and its interaction with §4.7

The brief's cap is not an independently chosen number; it is **derived from §4.7's reserved-first allocation**. Every node the brief reaches (§5.4) reserves its engine skeleton and structured data first; what remains is the overlay allowance, sub-capped per injection point. The brief's own cap is therefore the tightest of the per-node overlay allowances it must fit inside across every node it enters, measured — per §4.7 rule 3 — "at theme and playbook load," never at runtime, and never satisfied by truncation. This is why failure taxonomy item 5 (§4) is a distinct entry from item 9: item 5 is the brief's own single cap; item 9 is the *combined* overlay overflow once every injection point (of which the brief's content is one contributor among several) is composed for a specific node. A brief that individually fits its own cap can still, in combination with a large worked-example allowance on the same node, trigger item 9 — the two checks are independent and both run.

### 5.4 Injection points, nodes, and a real asymmetry

Per `CONDUCTOR_RULINGS.md` CR-3's table, the brief reaches **N-3, N-5, N-6** (hook, script, shot/slide list) via IP-1/IP-3/IP-5/IP-6/IP-7, and **N-7** (media prompt composition) via **IP-6 only**. The asymmetry is load-bearing and worth stating plainly: the brief can shape what a script *emphasises*, but for the image/video prompt it can only ever add to what to *avoid* (negative-prompt layer 3b, `ARCHITECTURE_PLAN.md` §4.10 and `03_pipeline_and_gates.md` §7.3) — never supply positive depiction guidance. No node outside this list ever sees any part of the brief; N-1, N-4 receive resolved selections only (no operator prose, per CR-3's own table), and N-2, N-8 through N-13 receive nothing, exactly as the depth table requires.

This document flags one genuine tension in CR-3's own wording as an open question rather than silently resolving it: each of IP-1 (role/genre framing), IP-3 (archetype brief, a registry selection), IP-5 (emphasis directives, drawn from a registry vocabulary) and IP-6 (additive banned constructions) is independently defined in `03_pipeline_and_gates.md` §4.2 as a **bounded, non-free-text slot** — a registry pick, a length-bounded descriptor, or an additive negative construction. None of those definitions, read alone, describes a place where a paragraph of open guidance naturally lands. This document's working resolution — used throughout this design — is that the brief is **one bounded field whose content is exposed to each node's prompt composer**, which decides how much of it surfaces inside each IP's own existing shape (e.g., a sentence of the brief becomes part of IP-1's bounded descriptor; another part restates as an IP-5 emphasis statement within its registered-vocabulary count), rather than five literal copies of the same text landing in five differently-typed slots. This is recorded as **CFG-OD-5** (§8), because it should be settled explicitly by whoever owns §4.2 before implementation, not inferred from this document alone.

### 5.5 Leak-checking and the fingerprint

The brief is compared against the theme's exemplar corpus at **every edit**, using the deterministic n-gram/named-entity overlap mechanism `ARCHITECTURE_PLAN.md` §6.11 already specifies for check class 11, applied proactively at config load rather than only at generation time — catching a brief that quotes corpus language before it ever reaches a node. Any overlap without a corresponding ledger entry is a leakage event, recorded exactly as §6.11 rule 2 requires. The brief's resolved content is one of the values folded into the per-node overlay fingerprint for every node it reaches (§4.4 of `03_pipeline_and_gates.md`); editing it therefore changes those nodes' fingerprints, forces new idempotency keys, and fires the regression gate (§1.4 step 4).

## 6. The safety proof

**The objection, stated at full strength:** the resolver is a model reading operator-authored prose, and its output configures gates. Operator prose therefore influences gate behaviour transitively, one hop removed from where CR-3 draws the line.

**This document concedes the objection is correct as a description of fact.** A wrong genre inference, or a substitution declaration wrongly accepted, does change what a downstream gate will pass, and that influence traces back to text the operator wrote. Denying this would be the same defect class P-10 already exposed once — asserting a mechanism "cannot" do something without naming where it is actually prevented (`00_MASTERPLAN.md` acceptance criterion C: "an assertion that a playbook 'cannot' is insufficient"). The concession is offered instead of a rebuttal that would not survive adversarial review, and it is paired with the mitigations that make the concession survivable.

**Why it does not reopen P-10.** P-10's mechanism was specific: a tenant wrote a claim directly into their own claim ledger, and the ledger's eleven check classes are all substantiation-shaped, so the tenant's own prose became **evidentiary content** a gate accepted as true. The resolver's output is categorically different in kind, not merely in degree: every value that reaches a gate through the resolver is a **selection from a closed, engine-owned, pre-calibrated registry** (`CONDUCTOR_RULINGS.md` CR-7: "the resolver selects from registries. It has no authoring power"; `00_MASTERPLAN.md` §11: "no tenant-authored gate criteria, claim classes or rubric variants. Registries are engine-owned; playbooks select"). Operator prose never becomes the *content* a gate evaluates — at most it becomes an *index* into a table the engine built, calibrated and versioned in advance. P-10's failure required the tenant's words to be believed; this design's worst case requires the tenant's words to be misclassified into a different pre-built bucket, which is a materially smaller and differently-shaped risk.

**Why the risk is bounded differently across the two registry classes it actually touches.** §2's Posture-A/B split matters here directly. For the criterion registry and the fact-schema profile — both Tier-1-adjacent — the resolver's selection power is asymmetric by construction: `03_pipeline_and_gates.md` §3.1 permits exactly four moves, three of which only ever add or strengthen a check, and this document's own recommendation (§2.1's boxed note) keeps bar strictness off the interpretation surface entirely in v1. A resolver misclassification here can make a gate **stricter than intended**, never looser — the transitive path is safety-monotonic for this half of the objection. For voice genre — the one registry `00_MASTERPLAN.md` §3.1 itself names as "a relaxation surface... strictness is not preserved here" — the objection has real teeth, and the mitigations are the ones already built into this design rather than newly invented for this section: registry-closure (six pre-calibrated genres, never a seventh authored on the fly), the elevated confidence floor (§2.3), calibration-gated scheduling (an uncalibrated genre "runs deliberately lenient... may never be scheduled," §4.5), and — the mitigation this whole document exists to specify — the mandatory, human-accepted, impact-ordered readback and diff (§3), which names voice-genre changes as the headline example precisely because this transitive path was anticipated, not discovered after the fact.

**Why it does not weaken the depth tiers.** The resolver adds no new channel into N-2 or N-8 through N-13. It is, instead, the mechanism that *guarantees* no such channel exists: a run "consumes an already-resolved config or refuses to start" (CR-2 property 1), and "the pipeline has no knowledge that an authoring form exists" (CR-1). What crosses from config-load into runtime is exclusively closed-vocabulary registry identities and validated literal arrays — indistinguishable in form from what a hand-picking, enum-literate operator would have produced under the ~180-knob surface this amendment replaces. The depth table's guarantee is about **free text** reaching those nodes, and the resolver's entire function is to ensure none survives past config-load.

**A related, narrower point worth naming.** Because the resolver is itself a model reading operator-influenced text, it is in principle exposed to prompt-injection attempts crafted into the authoring form. This does not enlarge the attack surface materially, because the resolver's own output vocabulary is exactly as closed as a gate node's: even a successful attempt to manipulate the resolver's own instructions can, at worst, cause it to select a wrong-but-still-registered member or to refuse — it cannot cause it to emit content outside its bounded output schema, because the resolver was designed under the same "structured slot-filling, never free output" discipline `03_pipeline_and_gates.md` §4.1 applies to nodes, even though it is not one.

**The strongest rebuttal element, and it is about provenance rather than mechanism.** P-10's defect was that authorship became **invisible** the moment a tenant's claim reached VERIFIED status in the ledger — nothing downstream distinguished an engine-verified fact from a tenant's own assertion once it was inside. This design does the opposite by construction: every resolved value carries a provenance tag (§2.0 — Named / Inferred / Defaulted / Refused) that survives into the resolved form, the readback, the diff, and the artifact-level pinning (`03_pipeline_and_gates.md` §4.4's seven-item version set, extended in §7 below to include the resolver itself). Operator-originated influence is never laundered into looking engine-native; it is permanently tagged, diffable and versioned. That is the direct answer to "laundering," even while the "transitive influence" fact itself stands conceded.

## 7. Cost and determinism

**Token cost per resolution.** The resolver's input is dominated by **registry context**, not operator prose — the authoring form itself is small by design (twelve Tier-A fields, three Tier-B fields, most of them picks or short arrays; only the brief and two guidance sentences are open-ended and each is capped, §5.3). The registries it must reference to classify against (the full angle taxonomy, the criterion families, the CTA table) are the larger and fixed-size input. Because both sides are bounded and enumerable — the same property `03_pipeline_and_gates.md` §5.4a relies on for pipeline nodes — resolution cost is itself computable in advance, on the same principle, without being one of the pipeline's own per-run ceilings. This document does not invent a figure; it states the order of magnitude qualitatively, on the same footing `ARCHITECTURE_PLAN.md` §5.2 uses for text calls generally: closer to a small handful of the pipeline's own judge-class calls than to a full pack run, reported as a **config-time cost, separately, never charged to a run's budget** (CR-2 property 5).

**How often it runs.** Triggered only by an authoring-form edit (CR-2 property 1) — not per run, not per artifact. In steady state this is rare relative to run cadence: a theme is edited occasionally (initial setup, a Tier-B tuning pass after a digest suggestion, a rare Tier-A change), while runs happen multiple times a week. The cost profile is bursty (concentrated at initial setup and at any playbook-kind migration) rather than continuous.

**Determinism.** The resolver must be **outcome-deterministic** across re-runs of byte-identical input — the same registry selections, the same confidence-tier classification, the same pass/fail verdict — even though it is not necessarily letter-for-letter deterministic in its explanatory prose, because the underlying model is not guaranteed deterministic at any sampling setting. Three things make outcome-determinism achievable rather than merely hoped for: the resolver's substantive output is a small discrete classification (a registry member, a confidence tier, a pass/fail) rather than open-ended generation, and discrete classification is materially more stable under resampling than prose; sampling is pinned to the most deterministic configuration available for the resolver's model role; and the resolver checks its own reliability reflexively — every resolution is compared against the immediately prior resolution for the same authoring-form fingerprint, and a divergence in the *selections* (not merely the explanatory prose) with no input change is itself flagged as a resolver-instability event, blocking auto-acceptance and forcing a human-reviewed re-resolution rather than silently accepting whichever run happened to complete first.

**Model pinning and upgrades.** The resolver's own model identity and version is recorded on the resolved config, on the same precedent `03_pipeline_and_gates.md` §4.4/§14.7 already establishes for pipeline-node model versions per role. A model upgrade does **not** retroactively invalidate an already-accepted resolved config — the resolved form, once accepted, is inert data (registry IDs, literal arrays, a brief), and inert data does not need re-interpretation to keep meaning what it meant. What changes going forward: the next authoring-form edit (or an explicit operator/conductor-requested re-resolution audit) uses the new model version, and if its output diverges from the prior resolution for unchanged text, that divergence surfaces through the same diff mechanism (§3.2) a genuine authoring-form edit would produce — even though the trigger was a model change rather than an operator change. Whether a model upgrade should instead force a **mandatory** re-resolution pass across every existing accepted theme is a real operational and cost decision this document does not settle — **CFG-OD-8**, §8.

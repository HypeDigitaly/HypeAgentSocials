## 1. What this means for the operator

This system will run by itself, at night, with nobody watching it — like an alarm clock that also has to decide, on its own, whether it's safe to spend your money before it rings. Four things have to be true for that to be safe. First, the machine needs a rock-solid idea of "what counts as one run" — including what day it thinks it is, in your timezone, even if the run happens to cross midnight — so it never confuses today's work with yesterday's. Second, if the same scheduled trigger fires twice, or you accidentally start it while it's still running, it must never double-charge you or double-post anything; it should simply notice something is already in progress and step aside. Third, every dollar spent on video/image generation gets written down immediately, in a small local record file (no database server to install or babysit), so that if the machine crashes ten minutes after paying for a video, the next run picks up exactly where it left off instead of throwing that money away or paying for it twice. Fourth, when something goes wrong, it needs to stop cleanly and tell you clearly what kind of "wrong" it was: "everything's fine, just go review the pack," "some sources were flaky today," "I stopped because I ran out of budget partway through," "I stopped because something looked unsafe or unclear about the brand," or "something actually broke and needs an engineer." A small always-on note file on disk, plus one active alert (an email or chat message), tells you which of those happened without you needing to dig through logs every morning. None of this requires a server, a database admin, or anything fancy — it's a handful of small local record files and one lock, doing their job quietly so the money and the work are never wasted by surprise.

## 2. Body

### 2.1 Orchestration paradigm

**Options considered:** (A) fully agentic loop — an LLM decides the next tool call at every step, with no fixed pipeline shape; (B) deterministic pipeline with narrow LLM nodes — a fixed stage graph (collect → rank → spin → generate → package) executed by ordinary control-flow code, where LLM calls are narrow, bounded leaf tasks ("score this topic," "write this caption") with defined input/output contracts; (C) hybrid — a deterministic backbone/state machine where an LLM is given bounded discretion *inside* a stage (e.g., a capped self-critique loop while drafting copy) but never controls stage sequencing, budget gating, or exit decisions.

**Tradeoffs, judged on cost determinism / testability / budget enforceability / unattended-cron safety / 3am debuggability:**

- **Fully agentic (A):** cost is emergent, not bounded in advance — a reasoning/tool-call loop can spiral, and nothing structurally stops the model from burning tokens before it ever reaches a spend-gated step. Testability is weak because the same input can produce different tool-call sequences run to run. Budget enforcement would have to be a tool the agent *chooses* to call, which is not enforcement. Unattended-cron safety is weak — no guaranteed fail-closed points, no guaranteed halting shape. 3am debuggability is poor: the artifact left behind is a free-form reasoning transcript, not a fixed stage name with a fixed log, so root-causing a failure means reading an open-ended trace rather than looking at "stage 3, checkpoint 2."
- **Deterministic pipeline with narrow LLM nodes (B):** cost is bounded before the run even starts — each stage has a fixed/capped number of LLM calls with per-call token and timeout ceilings, so a hard cost ceiling is computable up front. Testability is strong — each stage is a near-pure function with defined inputs/outputs, mockable and golden-file-testable independent of the others. Budget enforcement is pipeline code, not model discretion — checks happen at stage boundaries, which are fixed and guaranteed to execute. Unattended-cron safety is strong — every stage has a known, finite set of outcomes. 3am debuggability is strong — a crash is always "died in stage X, after checkpoint Y," with a bounded log for that stage alone.
- **Hybrid, bounded (C):** close to (B) on every axis, provided the "bounded autonomy" inside a stage has its own hard iteration/cost ceiling enforced by the surrounding pipeline code (not by the model's own judgment) and never touches stage sequencing or budget gating. Under that condition, cost determinism, testability, and safety remain effectively as strong as (B); only the inner trace of a single stage varies, and that variance is contained to one stage's log.

**Recommendation:** adopt **a deterministic pipeline with narrow, bounded LLM nodes as the backbone**, with the one hybrid concession that a small number of specific nodes (topic ranking, copy drafting) may run a short, hard-capped internal iteration (e.g., a bounded self-critique pass) as long as: the cap is enforced by pipeline code, not the model; the enclosing stage boundary, checkpoint, and budget gate are unaffected; and the entire inner loop is logged as part of that one stage's record. Overall stage sequencing, checkpointing, spend gating, and exit-code determination must remain pure pipeline code, never LLM-decided. This is the only shape that gives a computable pre-run cost ceiling, stage-level testability, and a 3am failure story that points at one named stage rather than an open-ended trace — all of which matter directly given the $50 trial budget and the requirement to fail closed unattended.

**Rejected alternatives:**
1. *Fully agentic loop as the primary orchestrator* — rejected because it cannot bound cost or guarantee a fail-closed halt before spend occurs, which conflicts directly with the trial-budget and unattended-safety constraints; non-deterministic tool-call sequencing also makes 3am postmortems disproportionately expensive to read.
2. *Full hybrid where an LLM-level planner may reorder, skip, or add pipeline stages* (e.g., "decide whether to skip research and rank from cache") — rejected because it reintroduces the same unbounded control-flow risk as the agentic loop, just at coarser granularity; stage sequencing and budget gating must stay in pipeline code for a system with no adult supervision at 3am.
3. *Multi-agent debate/critic-actor loops per stage as the Wave-1 default* — rejected for now as a cost multiplier (every extra pass adds tokens) with unproven ROI at trial-budget scale; deferred to a later, explicitly opt-in "quality mode" with its own separate budget ceiling once basic budget/ledger infrastructure is proven trustworthy in production.

### 2.2 Run identity: shape, timezone discipline, overlap policy, cross-platform locking

**What constitutes one run:** a single invocation of the console job for one theme, from secrets/theme load through package-write and exit-code emission. Conceptually, a run's identity is composed of theme identifier + run-date (a pinned logical day, see below) + an attempt/sequence number distinguishing a manual rerun from the original scheduled attempt for that same run-date. This identity is decided once, at the very start of the run, and carried unchanged through every stage, checkpoint, and ledger row — it is never recomputed mid-run.

**Timezone discipline — options:** (a) store and derive all timestamps in UTC internally, with a single configured "theme timezone" used only to derive the logical run-date and for human-facing display; (b) use local machine time throughout; (c) let each stage/component pick its own convention ad hoc.

- (a) UTC-internal + configured display timezone: portable across a Windows-now/Linux-later move (D-05), immune to locale differences between machines, and avoids the classic scheduler gotcha where a job scheduled at a fixed local wall-clock time runs twice or zero times on a daylight-saving-time transition night (a documented risk on both Windows Task Scheduler and Linux cron/systemd-timers when schedules are expressed in local time).
- (b) Local machine time throughout: easiest to eyeball in raw logs, but breaks on DST transition nights and breaks the moment the Windows box is replaced by a Linux server in a different timezone, directly violating the cross-platform mandate.
- (c) Ad hoc per component: trivially inconsistent — different stages could disagree on "today," corrupting any dedupe index keyed by date.

**Recommendation:** UTC for every stored timestamp (run start, checkpoints, ledger rows); derive the run-date once, at run start, from a single configured theme timezone; never recompute run-date mid-run even if wall-clock execution crosses midnight. Run-date (the logical day this run represents, used for dedupe/freshness) is a distinct concept from wall-clock time (the actual instant used for log timestamps, retry backoff, and checkpoint staleness) — both are needed, and conflating them breaks dedupe the moment a run straddles midnight or is manually rerun "for yesterday."

**Rejected:** (b) local-machine-time-as-canonical — rejected due to DST double-run/skip risk on both target schedulers and because it breaks portability the moment the deployment moves to a Linux server in a different timezone (D-05). (c) per-stage ad hoc "now" — rejected because a run straddling midnight could produce two different "today" values across its own artifacts, silently corrupting the cross-day dedupe index.

**Overlap policy when the previous run is still going — options:** skip the new invocation entirely; queue it to run after the current one finishes; kill the running one and start fresh.

- Skip: safest for a money-spending pipeline — avoids two runs racing on the same ledger/spend cap and avoids the specific risk of both runs reaching a media stage and each billing independently.
- Queue: reasonable for CPU-only jobs, but this pipeline can legitimately run long (research + LLM + minutes-long async media), so queuing risks an unbounded backlog if a run hangs, silently piling up paid, near-duplicate runs to fire back-to-back once the block clears.
- Kill-and-restart: actively dangerous here — it can kill a run mid-media-generation, orphaning already-submitted, already-paid-for async media jobs and leaving spend-ledger rows with no completing pipeline left to reconcile them. This is exactly the "crash must not discard paid work" failure mode, self-inflicted.

**Recommendation:** **skip** by default — do not start a new run while a live-run lock is held; log and notify the skip event distinctly from both success and failure. Provide a separate, explicitly operator-invoked "queue behind the current run" affordance for manual reruns only — never for the automatic cron/Task-Scheduler trigger path. Never auto-kill a running instance.

**Rejected:** kill-and-restart — rejected because it directly risks discarding paid, in-flight media jobs and corrupting the spend ledger's consistency. Unbounded auto-queue with no cap or visibility — rejected because a genuinely stuck run (e.g., hung polling a slow media provider) would let queued triggers accumulate silently, eventually firing a burst of stale, back-to-back automated (paid) runs the moment the block clears, with no human having noticed anything was wrong in the meantime.

**Cross-platform locking mechanism — options:**

- *Windows:* a named/global OS mutex; an exclusively-opened lock file whose handle is held for the process's lifetime and is released by the OS automatically on process exit or crash; a PID-plus-start-time lock file checked against a manual staleness timeout (a weaker, purely advisory convention).
- *Linux:* an advisory lock held on an open file descriptor for the process's lifetime, auto-released by the OS on exit or crash; a PID-file-only convention checked against process liveness; a lock row inside the run ledger itself, using a database transaction as the mutual-exclusion primitive.

**Recommendation:** use an **OS-mediated exclusive lock held on a dedicated run-lock file for the life of the process** on both platforms — Windows exclusive file-open/share-deny and Linux advisory file locking are directly analogous, kernel-guaranteed-release-on-crash primitives, so the same conceptual mechanism satisfies D-05 without needing a database server. Layer a second, ledger-recorded "run started, not yet completed" row on top as a belt-and-suspenders check, independent of whether the lock-file mechanism is trusted in a given edge case.

**Rejected:** PID-file-only convention with a manual staleness timeout — rejected on both platforms because PID reuse after a reboot and clock-based staleness heuristics produce both false "still running" and false "safe to start" verdicts, a well-known source of flaky ops tooling. Relying solely on a ledger-row lock inside an embedded database with no OS-level file lock — rejected as the sole mechanism because it does not protect against two processes racing before the ledger file itself is even opened, and gives no OS-guaranteed release if the database file is left in a locked or inconsistent state after an abrupt power loss.

### 2.3 Idempotency + dedupe keys per stage

**The problem:** the same cron/Task-Scheduler trigger can fire twice (retrigger, manual rerun of the same slot), and a retried run must not re-research, re-generate, or re-bill work that was already done.

**Options for "how do we recognize already-done work":** (a) content-hash-based identity — hash the semantic input to a stage plus the relevant config/prompt-template version; (b) natural-key-based identity — theme + run-date + stage name, regardless of whether the underlying inputs subtly changed; (c) purely time-window-based — "don't redo this if it happened within the last N hours," with no structural identity at all.

- (a) Content-hash: correctly reuses output when nothing meaningful changed (robust to cosmetic config edits) and correctly invalidates the cache when something material changed (new brand-truth snapshot, edited prompt template) — the most correct option, at the cost of needing a disciplined definition of "what counts as input" per stage.
- (b) Natural-key only: simple, but a same-day rerun after a deliberate mid-day config or brand-truth fix would incorrectly reuse stale output — a real risk given "ambiguous/incorrect brand truth" is elsewhere a fail-closed trigger, not something that should be silently papered over by a stale cache hit.
- (c) Time-window only: cannot distinguish "the exact same request repeated" from "a legitimately different, closely-spaced request" — it either over-suppresses legitimate reruns or under-suppresses true duplicates, and for money-spending stages that ambiguity is unacceptable.

**Recommendation:** **content-hash-based keys** for every cost-bearing stage, composed of theme id + run-date + a stage-defined semantic input hash + config/prompt-template version. Natural keys (run id + stage name) remain useful as a human-facing lookup index but must not be the sole identity for correctness.

**Rejected:** natural-key-only identity — rejected as the sole mechanism because it cannot detect a legitimate need to redo a stage after a same-day brand-truth or config correction, risking content silently shipped against stale or wrong brand truth. Purely time-window heuristics — rejected as the sole mechanism for any money-spending stage because they cannot reliably tell a true duplicate cron fire apart from an intentional, closely-spaced manual rerun.

**Per-stage key design:**

- *Research/collection:* theme + source + query/topic-signature + run-date (or a config-controlled rolling freshness window); a retry recognizes existing raw captures for the same run-date and skips or deltas rather than re-hitting rate-limited APIs.
- *Ranking:* hash of the input artifact set + ranking-config version; unchanged inputs reuse the prior ranking output rather than recomputing (saving LLM-scoring cost on a retry too).
- *Cross-day topic dedupe* (recognizing the same underlying angle resurfacing days later): a separate index keyed by a normalized topic/angle signature (not raw string match) with a configurable lookback window — distinct from within-run retry idempotency; covered further under the ledger set below.
- *Spin:* ranked-topic id + brand-truth-snapshot id + theme voice-config version; unchanged inputs on retry reuse prior spin output.
- *Asset/content generation (copy, carousel/shot-list plans, scripts):* spin-output id + platform/asset-type + prompt-template version.
- *Media generation (the expensive stage):* asset-plan id + provider + prompt/job-spec hash + a client-supplied idempotency token passed to the provider's job-submission call, checked against the media-job ledger before ever submitting a new provider call. This is the single most important dedupe key in the system given real money is on the line — a retry must be provably recognized as "already submitted" before a second billable submission is attempted.
- *Packaging:* run id + set of included asset ids — idempotent by construction; re-running it against unchanged upstream artifacts reproduces the same package rather than forking a diverging duplicate.
- *Notification:* run id + notification type ("pack ready," "run failed"); a retried run checks for an "already sent" marker before sending, so the operator is never double-pinged for the same event.

### 2.4 The ledger set — substrate options

Eight record types need a home: research-artifact store, cross-day topic-dedupe index, run ledger, async media-job ledger, spend ledger, pack outputs, brand-truth snapshots, review-decision state. **Options evaluated for each: SQLite (a single-file, serverless, transactional embedded engine); plain files (one record per file, directories organized by run-date/type); a non-SQLite embedded key-value/document engine.**

**General tradeoffs (apply throughout):**

- *SQLite* — no server or service to install/administer (fits D-07 directly), single file, full transactional (ACID) guarantees so a checkpoint write either fully commits or fully rolls back (exactly the crash-consistency guarantee needed for "a 04:00 crash must not discard paid work" bookkeeping), indexed queries for fast lookups (cross-day dedupe checks, spend totals, "jobs nearing URL expiry"), identical behavior on Windows and Linux today and later (D-05), and trivially backed up as a plain file copy. Cost: a binary file is harder to eyeball/diff directly than a text file, and it adds one small query-layer dependency.
- *Plain files* — maximally transparent (an operator can open a folder and read exactly what happened in a text editor), trivially portable and version-control-diffable for anything meant to be human-reviewed, zero query-engine dependency. Cost: no transactional guarantee across multiple related writes without careful atomic-write discipline (write-to-temp-then-rename, whose exact semantics differ subtly between Windows and POSIX and must be deliberately engineered on both); querying/aggregating across many small files (e.g., "total spend today," "has this topic appeared in the last 14 days") means scanning files or hand-rolling an index, which slows and gets error-prone as history grows.
- *Non-SQLite embedded engine* — sometimes offers schema-less storage matching heterogeneous record shapes out of the box. Cost: less universally available/documented than SQLite for this project's stack, thinner inspection-tooling ecosystem for a non-DBA solo operator, less uniformly production-proven crash-consistency than SQLite's decades of hardening, and a second data-access paradigm to learn/maintain — added long-term toil for a one-person team.

**Per-artifact recommendation:**

| Ledger | Recommended substrate | Why |
|---|---|---|
| Research-artifact store (raw captures) | Plain files, one artifact/batch per file, organized by run-date/source; existence+checksum indexed as rows in the run ledger (SQLite) | Bulky, heterogeneous, write-once/append-mostly content that benefits from direct human/text inspection during a scraping-breakage debug session; transactional weakness matters least here since writes aren't multi-field updates |
| Cross-day topic-dedupe index | SQLite | Needs a fast indexed "has this normalized signature appeared within the lookback window" query across months of history — exactly what flat-file directory scans handle poorly; recording "topic used today" must be atomic with the ranking decision that used it |
| Run ledger (one row per run: id, run-date, theme, timestamps, exit class, checkpoint state) | SQLite | The scheduler/monitoring backbone; needs transactional checkpoint updates so a crash mid-write leaves a consistent last-known checkpoint, not a torn record |
| Async media-job ledger (submitted/polling/completed/downloaded/failed, expiring URL) | SQLite, most strongly of all | A live per-job state machine that must transactionally agree with the spend ledger on what was actually billed, must support safe re-polling across process restarts, and must support an efficient "find jobs nearing expiry, not yet downloaded" query on every run start — trivial as an indexed query, error-prone as a directory scan |
| Spend ledger (money) | SQLite, non-negotiably transactional | Every paid call recorded as a row (run id, stage, provider, job id, amount, timestamp, reserved/committed/refunded status) inside a transaction that also updates a running total — a torn write here has direct financial-integrity consequences |
| Pack outputs (human review bundle) | Plain files, one self-contained bundle per run/topic; status indexed as a row in SQLite | This is what a human directly opens, reads, and annotates — should be maximally transparent, portable (attachable, copyable, diffable), and readable with nothing more than a file browser and text/markdown viewer |
| Brand-truth snapshots | Plain files for the human-readable snapshot content + a metadata row in SQLite (snapshot id, run id, timestamp, confidence, source-agreement status) | The content needs to be inspectable during a claim-safety dispute or postmortem; other stages reference "snapshot id N" as a fast structured lookup without re-parsing the file, and the "ambiguous brand truth → fail closed" rule is enforced against the structured row, not a file scan |
| Review-decision state (approve/reject/partial per pack/asset) | SQLite | Inherently relational and status-driven (a pack has N assets each with independent approval state referenced by downstream staging logic); benefits from transactional multi-field updates so a reviewer approving several assets in one sitting can't be left half-applied by a crash |

**Solo-operator reality (D-05, D-07):** SQLite is recommended everywhere structured/transactional querying matters specifically because it requires no install, no service, no port, and no DBA — it is a file that ships next to the run, is backed up by copying it, and is equally available unmodified on the future Linux server. Plain files are recommended specifically where human-readability of the *content itself* (not just metadata about it) is the primary requirement.

**Rejected alternatives:**
1. A client-server relational database for all ledgers — rejected because it requires installing, running, and administering a database service on a solo operator's machine (violates D-07 directly), adding a background service that itself needs monitoring/restart handling, disproportionate to this system's actual data volume and single-active-writer concurrency model.
2. Storing everything, including the spend and media-job ledgers, as plain flat files with no embedded database anywhere — rejected because those two ledgers specifically need atomic multi-field updates and fast conditional queries (approaching URL expiry, running total vs. cap) that flat files can only approximate with fragile, hand-rolled locking/indexing code — unnecessary reinvention of a solved problem.
3. A non-SQLite embedded document/key-value engine for the structured ledgers — rejected in favor of SQLite for this project's cross-platform (Windows-now, Linux-later) and solo-maintenance requirements: broader documentation, a more mature inspection-tooling ecosystem for a non-DBA operator, and more extensively production-proven crash-consistency for money-relevant records.

### 2.5 Run duration vs cadence; per-stage timeouts; stage-level checkpoint/resume

**Run duration vs cadence:** total run duration is highly variable — plausibly a few minutes with media generation skipped/dry-run, to well over an hour if several video jobs run serially. Cadence (how often the schedule fires per theme) is a product/config decision, deferred here, but the architecture must not treat "cadence is always longer than worst-case run time" as a safety guarantee — that assumption breaks the first time a provider is unusually slow. Instead, safety against overlap comes from the run-lock plus skip-on-overlap policy (2.2), decoupling cadence choice from correctness.

**Per-stage timeouts — options:** (a) one global run-level timeout only; (b) per-stage timeouts only, no overall ceiling; (c) both, nested — per-stage ceilings inside an overall run ceiling.

- (a) Global only: a single hung research source or media poll can consume the entire run's time allowance, starving later stages — including packaging, which might never run even though the expensive, already-paid-for media work genuinely finished. This is "crash discards paid work" realized via a timeout instead of a crash.
- (b) Per-stage only, no overall ceiling: prevents a single-stage hang from consuming everything, but gives no predictable total run length, which matters for an operator wanting an assured "done by morning" window, and interacts badly with overlap policy (an unexpectedly long "successful" run can cause the *next* scheduled trigger to be silently skipped).
- (c) Both, nested (recommended): each stage (per-source collection, per-call LLM node, per-job media poll) has its own ceiling; an overall run ceiling wraps all of them and, on approach, triggers a graceful wind-down — stop starting new paid work, checkpoint in-flight items for later resume, package whatever is complete — rather than an abrupt kill.

**Recommendation:** per-stage timeouts nested inside an overall run ceiling, with graceful wind-down (not hard kill) as the approaching-limit behavior, directly protecting the "must not discard paid work" constraint.

**Rejected:** global-timeout-only — rejected because one slow dependency can prevent packaging of otherwise-complete, already-paid work. Per-stage-only with no overall ceiling — rejected because it gives no predictable upper bound on total unattended run length and interacts badly with the overlap/skip policy by risking silent skips of the next scheduled trigger.

**Stage-level checkpoint/resume — the explicit scenario:** a 04:00 crash after roughly $10 of media generation must not discard that paid work. **Granularity options:** (a) whole-run checkpoint (restart from the very start); (b) whole-stage checkpoint (resume from the start of the failed stage only); (c) per-unit-of-work checkpoint (per individual job/source/asset within a stage).

- (a) Whole-run only: unacceptable given the explicit constraint — a crash mid-media-generation forces a full restart that either wastes the already-spent money (if it can't tell what's done) or, absent proper dedupe keys, double-spends by resubmitting the same jobs.
- (b) Whole-stage: better, but still requires consulting the media-job ledger to know which specific jobs already completed before the crash — at which point the real granularity in use is already per-job, just described at the coarser "stage" level.
- (c) Per-unit-of-work (recommended): each individual paid unit — one media job, one source fetch, one asset draft — is checkpointed the instant its ledger row transitions state (submitted → polling → completed → downloaded/archived, or failed), independent of whether the surrounding stage as a whole finishes. On resume, the pipeline re-enters the stage and asks the relevant ledger what's terminal, what's pending, and what never started, acting only on the incomplete remainder.

**Recommendation:** per-unit-of-work checkpointing, driven directly by the media-job ledger (and equivalent per-item ledgers for collection/generation) — the only granularity that satisfies "a crash after $10 of spend must not discard that $10."

**Rejected:** whole-run-only checkpointing — rejected outright as incompatible with the stated constraint; restarting from zero either wastes the spend or requires the same fine-grained dedupe checks anyway. Whole-stage-only checkpointing without job-level state tracking — rejected because "resume the stage" is meaningless without sub-stage state; without it, a stage-level resume either blindly redoes the whole stage (wasting spend) or needs the same fine-grained ledger anyway, making stage-level-only an incomplete half-measure.

*Illustrative state flow (prose, not code):* a media job moves submitted → polling → completed-pending-download → downloaded/archived, or diverts to failed/expired at any point; the media-job ledger row is the single source of truth for where a given job sits on that path, and resume logic reads that row rather than re-deriving state from scratch.

### 2.6 Exit-code taxonomy

**Options for granularity:** (a) binary success/failure only; (b) a small, fixed set of named outcome classes; (c) a large number of granular per-stage-per-reason codes.

- (a) Binary only: simplest for a scheduler's trigger logic, but destroys exactly the information a solo operator needs — "go look now" vs. "fine, just review" vs. "machine is broken" all collapse into one bit, forcing a log check after every single run.
- (b) Small named class set (recommended): enough differentiation to drive different responses — alert loudly on hard failure and policy-stop, log-only on degraded-sources, no-op on skipped-overlap — while staying small enough to memorize and map onto a scheduler's coarse exit-code signal.
- (c) Highly granular per-stage-per-reason codes: theoretically richer, but pushes detail into a channel (the OS process exit code) poorly suited to carrying it; most of that detail duplicates what the run-ledger row already records and is better carried there.

**Recommendation:** a small, fixed set of named classes — success; partial-success (degraded sources); partial-success (budget-capped mid-pack); policy-stop; budget-stop (pre-emptive, before any new spend in the affected stage); skipped-overlap (not a failure); hard-failure (infrastructure/technical) — each mapped to one distinct exit code for scheduler-level monitoring, with full detail (which source degraded, which policy tripped, exact stage/reason) recorded as structured fields in the run ledger, not encoded into the exit code itself. The exit code answers "what kind of outcome, at a glance"; the ledger answers "exactly why."

Distinguishing budget-stop (pre-emptive — the pre-run/pre-stage check refuses to start a stage at all because even one more unit would exceed remaining budget, so no new spend occurs) from partial-success-budget-capped (some assets were already produced before the cap tripped mid-pack) matters operationally: one means "we got partial value for the spend," the other means "we got nothing new this stage because the budget was already gone going in."

**Rejected:** binary success/failure only — rejected because it cannot distinguish "needs a human to fix config/brand-truth right now" from "everything's fine" from "budget ran out, nothing's wrong," forcing manual log inspection after every run and defeating the point of automated monitoring. Highly granular per-stage-per-reason numeric codes as the primary signal — rejected because that level of detail belongs in the structured run ledger, not in a channel (the OS exit code) that schedulers and monitoring rules are built to treat coarsely.

### 2.7 Unattended secrets

No interactive session exists at 03:00 to type a password. **Windows options:** task-level environment variables set in the scheduled task definition (or a wrapping launcher script that sets them from a protected source before invoking the console app); Windows' native per-user/per-machine data-protection capability (DPAPI) to encrypt secret material at rest, tied to the account the scheduled task runs as; an ACL-restricted plain secrets file, readable only by the specific Windows account the task runs under. **Linux options (for the later server deployment):** a plain environment file loaded at process start, permission-restricted to the service account; systemd-managed credentials, a native systemd facility for supplying secret material to a unit at start time without exposing it via general process-environment inspection; a dedicated external secrets-manager service reached over an authenticated channel at run start.

**Tradeoffs:** task/process-level environment variables are simplest but more exposed to casual inspection (by other tooling, by anyone able to view the task definition or a process listing) and easy to accidentally leak into diagnostic logs or crash dumps that capture environment state. DPAPI ties protection to the OS's own account/machine-bound key, working well with a task configured to run whether the user is logged on or not, but is Windows-only. ACL-restricted files are simple, human-inspectable by the right account, portable in concept, and their failure mode ("worked interactively, failed from the scheduler") is a well-understood, checkable configuration issue rather than a structural weakness. systemd credentials avoid plain environment-variable exposure and integrate tightly with systemd timers specifically, but are systemd-specific (no help if the Linux deployment ever uses bare cron) and have no Windows analogue, so cannot be the sole cross-platform mechanism. An external secrets manager gives the strongest separation, audit trail, and rotation story, but is disproportionate infrastructure for a solo operator with no server (D-07) and introduces a new externally-reachable dependency — itself a new unattended-failure mode ("secrets manager unreachable at 3am") to design fail-closed behavior around.

**Recommendation:** **ACL/permission-restricted secret files as the portable cross-platform baseline** — NTFS ACLs on Windows restricting read access to the task's run-as account; POSIX file permissions restricting read access to the service account on Linux. This is the one mechanism with a near-identical shape on both operating systems (a file, readable only by the exact account the unattended job runs as, kept outside source control), satisfying the cross-platform mandate without depending on a Windows-only or Linux-only primitive as the sole store. Layer OS-native hardening on top where low-effort and available (DPAPI-protect the Windows secrets file's contents at rest; adopt systemd credentials once systemd timers are confirmed as the Linux scheduler) as an enhancement, not a replacement, so the pipeline's secret-loading logic has one portable contract regardless of platform. As a hard design rule independent of storage mechanism: secrets are never placed in source control, never embedded in prompts sent to any LLM, never written into the run ledger, and are redacted from all logging paths.

**Rejected:** relying solely on task-level/process-level environment variables with no file-permission or OS-protection layer — rejected because they are more exposed to casual inspection than a permission-restricted file and easy to leak into diagnostic logs or crash dumps. Relying solely on an external secrets-manager service from day one — rejected at this project's current scale (solo operator, no server infrastructure, D-07) because it adds a new externally-reachable dependency and a new unattended-failure mode disproportionate to the actual secret volume and team size; revisit once operations grow beyond one person/one machine or compliance needs demand it.

### 2.8 Retries + partial-failure semantics per stage; budget caps including mid-pack cap-hit

**General retry-policy shape — options:** fixed-count immediate retry with no delay; exponential backoff with a capped attempt count and a capped total retry-time budget; unlimited retry until success or stage timeout.

- Fixed-count immediate retry: simplest, but for transient network/rate-limit conditions it can worsen things (hammering a source right after it signals "back off" tends to extend the throttling) and wastes stage-timeout budget retrying a fully-down endpoint with zero chance of success.
- Exponential backoff, capped attempts and capped total retry time (recommended default for submission-type calls): spaces retries so transient conditions can clear, while the caps prevent one misbehaving dependency from consuming the whole stage/run time budget.
- Unlimited retry until stage timeout: appropriate only for the narrow, specific case of *polling* an already-submitted async media job for completion — that is a different operation from retrying a paid submission, and must never be confused with it.

**Recommendation:** exponential backoff with capped attempts/time as the default for all *submission*-type calls (research fetch, LLM call, media-job submission), explicitly distinguished from *polling* an already-submitted async job (a patient, bounded-duration loop against the job's own expected completion window). Conflating the two is a real risk: a naive retry wrapper applied to a submission call could resubmit and double-bill a job that actually succeeded on the provider side but whose response was merely slow or malformed to read — exactly why idempotency tokens on submission calls (2.3) matter.

**Rejected:** fixed-count immediate retry with no backoff as the default — rejected because it worsens transient rate-limit conditions and wastes timeout budget hammering fully-down dependencies. Unlimited retry until stage timeout applied uniformly to all call types including paid submissions — rejected because, without the submission/poll distinction, a slow-but-actually-succeeded paid call risks being resubmitted and double-billed purely because its response was slow to arrive.

**Per-failure-type semantics:**

- *Research source down* (API error, browser-automation breakage): a per-source soft failure — log it, mark that source's contribution as degraded/missing in the run ledger and the pack, continue with remaining sources. Do not hard-fail the whole run for one dead source; this is what produces the partial-success (degraded-sources) exit class. Rejected: hard-failing the entire run whenever any single configured source is unavailable — rejected because it makes the whole pipeline hostage to the flakiest, most scrape-fragile source in the list, turning routine third-party flakiness into full-run outages requiring human intervention every time.
- *LLM error* (provider error, malformed output, timeout): retry with backoff up to a capped count for that specific call; if still failing, treat it as a failure of that one unit of work (that one asset's draft) — mark it incomplete in the pack rather than fabricating filler content — and let the rest of the stage's units proceed independently. Escalate to a full stage/run failure only if a configurable share of units in the stage fail, such that the resulting pack would be too degraded to be meaningful.
- *Media provider failure* (submission rejected, job errors out, job stuck, download URL expiring before download): submission-time failures follow the capped-retry-with-idempotency-token approach; a job erroring after successful submission is recorded as failed in the media-job ledger with no further billing assumed beyond what was actually charged, and is surfaced to the human as "this destination's media failed, here's why" rather than silently dropped. A job whose download URL is at risk of expiring must be prioritized for download immediately on resume — losing a paid-for asset's URL after the fact is pure waste, which is exactly why the media-job ledger's "find jobs nearing expiry" query (2.4) matters operationally.
- *Disk full:* a hard-failure class, not a per-unit soft failure, because it risks corrupting in-progress writes to any ledger or artifact file. Correct behavior is a proactive low-disk-space check at run start and again before entering the media stage specifically (the largest space consumer), failing closed *before* further writes once a safe threshold is crossed. Rejected: reacting to disk-full errors only after they occur — rejected because by the time a write fails, a ledger transaction may already be partially applied, and media generation can consume disk fast enough that reactive-only handling risks exactly the mid-media-stage, financially-relevant corruption this design exists to avoid.

**Budget caps, including the mid-pack cap-hit case (cap trips with 3 of 6 destinations generated) — options:** (a) ship the partial pack, clearly marked incomplete, with the 3 completed destinations reviewable and the other 3 explicitly flagged as not-generated-due-to-budget; (b) withhold the entire pack until an operator manually raises the cap and reruns to complete the remainder; (c) roll back/discard the 3 already-generated (and already-paid-for) destinations for an "all or nothing" pack.

- (a) preserves the value of money already spent and gives the operator an informed choice (approve the 3 as-is, or explicitly raise the cap and rerun for the rest) — directly aligned with "a capped run must not discard paid work."
- (b) wastes the review-readiness of 3 already-good, already-paid destinations purely because a 4th tripped the cap, and risks the pack never being completed if the operator forgets to follow up.
- (c) is the worst option financially — it throws away money already spent, purely for pack-shape consistency.

**Recommendation:** **(a) ship the partial pack**, with the pack's own status field and the run's exit class (partial-success, budget-capped) making unambiguous exactly which destinations are missing and why (budget, not error), plus the cheapest completion path (raise this run's cap and rerun only the missing destinations, an explicit operator action, never automatic). The spend ledger records the 3 completed destinations' actual cost and separately marks the cap event itself (the blocked 4th attempt), so future budget analysis can see both what was spent and what was deliberately withheld.

**Rejected:** withholding the entire pack until manually completed — rejected because it delays or risks losing the reviewable value of already-paid-for work with no offsetting benefit. Rolling back/discarding the completed destinations for consistency — rejected outright as the most direct possible violation of the paid-work-preservation constraint, converting a partial, valuable result into a total loss for aesthetic uniformity alone.

### 2.9 Notification substrate

**Options:** a filesystem flag (a marker/status file or "latest pack" pointer, always written); email; a webhook/chat-platform message (posting to a channel via an incoming webhook); a native OS-level desktop notification.

- Filesystem flag: zero external dependency, works even with no network or configured channel — a necessary property, since a notification mechanism must never itself fail silently in a way that leaves the operator believing nothing happened — and identical in concept on Windows and Linux. Purely passive, though: it does nothing to actively alert; it only helps once the operator thinks to check.
- Email: actively pushes a notice without requiring the operator to remember to look, works from an unattended machine with just outbound network and credentials, and suits a familiar "nightly report" pattern. It is itself a dependency (mail relay/credentials) and can be missed/buried without careful subject-line discipline.
- Webhook/chat message: fast, mobile-friendly, and likely to be noticed sooner than email for a solo operator who checks chat apps often — but adds a third-party service dependency (an outage or revoked webhook silently breaks notification unless paired with the filesystem-flag baseline) and needs its own secret handling (2.7).
- Desktop/OS notification: immediate and highly visible *if* the operator is at the machine, which is precisely not the case for an unattended overnight run; depends on console/session state that may differ under a task configured to run whether logged on or not. A reasonable addition for daytime interactive runs, not a reliable primary channel for unattended nightly ones.

**Recommendation:** a **layered approach** — the filesystem flag as the mandatory, always-present baseline (requires nothing external, so it cannot itself fail to be produced) plus one configurable push channel (email or chat webhook — a config choice, not an architectural fork, since both are simply "call this notification sender at run end") for both "pack ready" and "run failed/policy-stop" events. A failure to deliver the push notification is itself logged and reflected in the run ledger but must **not** change the run's own success/failure exit class — a notification-delivery failure must never be confused with a pipeline failure. The filesystem flag/run ledger remains ground truth of "did today's run happen," independent of whether the push notification got through. Desktop notification is a reasonable later add-on for interactive/daytime runs, not the unattended-run primary channel.

**Rejected:** desktop/OS notification as the sole or primary channel — rejected because it is only effective while someone is at the console, which is definitionally not true for the unattended overnight runs this system is built around. A push channel (email/webhook) as the sole channel with no filesystem-flag baseline — rejected because the push channel is itself a dependency that can fail silently (credential expiry, service outage, revoked webhook), and without an independent, dependency-free baseline record, such a failure could leave the operator with no record at all that a run happened — a strictly worse failure mode than a missed push notification alongside an accurate local status file.

### 2.10 Missed-run catch-up semantics

**Scheduler-level behavior:** Windows Task Scheduler has a configurable option to run a missed scheduled task as soon as the system is next available (a catch-up setting), alongside a default/alternate behavior of simply skipping to the next scheduled occurrence, depending on task configuration. Bare Linux cron fires only if the system/cron daemon is running at the scheduled minute — if the machine is off, that firing is simply lost, with no built-in memory of it. Linux systemd timers, by contrast, support a persistent option that does remember and catch up a missed run at next boot/wake — closer to Task Scheduler's behavior than bare cron is. This creates a genuine cross-platform asymmetry (Windows Task Scheduler and systemd timers can both catch up; bare cron cannot), which matters given the cross-platform mandate (D-05) and the ambiguity in whether "Linux server cron later" means literally bare cron or a scheduler equivalent.

**Options for what the *pipeline itself* should do about a missed window, independent of the OS scheduler:** (a) treat missed and on-time invocations identically, with no pipeline-level catch-up logic, relying entirely on whatever the OS scheduler's catch-up setting does or doesn't do; (b) pipeline-level full backfill — detect every missed run-date via the run ledger and run once for each, up to some cap; (c) pipeline-level "skip missed, single current-window run" — detect that windows were missed, do not backfill each one, simply run once for "now," and explicitly record in the run ledger how many windows were missed.

- (a) is fragile and platform-inconsistent given the asymmetry above, and worse, if the OS *does* catch up, the pipeline has no special awareness that the resulting research is stale relative to its own freshness assumption (freshness is an explicit input to the ranking formula, attention × brand fit × freshness) — a naive catch-up run days later could research and spin "yesterday's viral topic" as if it were today's, a content-quality problem, not just an ops one.
- (b) risks a burst of consecutive automated, paid runs firing back-to-back the moment the machine is next on, each representing real spend with no pacing safeguard, and again chases stale freshness windows for days already past.
- (c) respects that content value decays with topic freshness (little point re-researching "what was viral three days ago" as today's signal), avoids a burst of paid runs on wake, and still gives the operator honest visibility ("3 scheduled windows were missed while the machine was off") via the ledger/notification rather than silently pretending nothing was missed.

**Recommendation:** **pipeline-level "skip missed, single current-window run"** as the default, regardless of the OS scheduler's own catch-up configuration — the pipeline's own run-ledger logic, not an OS quirk, decides whether an invocation is "actually run a full pipeline" or "just note that time passed," which behaves consistently across Windows Task Scheduler, systemd timers, and bare cron alike. Treat OS-level "run missed task ASAP" settings as harmless if left enabled, since the pipeline's own dedupe/ledger logic will recognize an unexpected extra invocation and apply the same skip-missed reasoning to it.

**Rejected:** relying solely on the OS scheduler's catch-up setting — rejected because it produces platform-inconsistent behavior (satisfying D-05 on one platform, violating it on another) and, when it does fire, carries no product-level awareness that the resulting research is stale. Pipeline-level full backfill of every missed run-date — rejected because it produces uncontrolled bursts of paid, automated runs immediately on machine wake with no pacing safeguard, and evaluates mostly already-stale "viral" signal, undermining the freshness term the ranking formula depends on.
